# 统一评分标准 v1.0：50%完整交付奖励

采纳日期：2026-11-09。规范版本：`1.0.0`；计分修订标识：`delivery-bonus-50-v1`。

**本规范已采纳；旧评分器迁移须独立版本化。本文发布不表示各历史 verifier 已经自动启用新规则，也不覆盖旧成绩。** 本规范统一评估与计分方式，不修改任务说明、输入、业务算法、返回值或既有接口契约。

## 1. 四项指标分别报告

| 指标 | 要回答的问题 | 单次结果 |
|---|---|---|
| 公开通过 Public Pass | 干净提交能否跑通公开验收入口？ | 0或1 |
| 核心转换用例通过率 Core Transform Case Pass Rate | 直接调用核心转换函数的冻结用例通过多少？ | 通过数/固定用例数；不适用为N/A |
| 严格通过 Strict Pass | 整题是否满足全部核心交付契约？ | 0或1 |
| Reward | 核心验收取得多少部分进展，是否完整交付？ | 0至冻结的单题上限W，支持小数 |

原先展示的“API acc”统一改名为**核心转换用例通过率**。它不能被解释为所有公开接口均正确。核心转换用例全部通过，仍可能存在加载、构建、命令行执行或产物错误。

## 2. 发布前冻结验收清单

每题注册以下核心集合。每个注册单元有唯一ID、类别、适用契约、执行方法、固定用例或其生成规则，以及评测方保存的期望结果和摘要。

| 集合 | 范围 | Reward计分单位 |
|---|---|---|
| A：核心转换 | 直接调用transform的正常、边界及业务输入有效性用例 | 每个冻结用例1个verifier |
| B：接口 | load_payload、build_component及适用时的parser兼容性 | 每组件1个bundle，内部全部通过才算该单元通过 |
| D：产物及集成 | 组件产物、core_manifest、final_report，或任务已有的其他模块/集成验收 | 每个冻结产物、模块或集成检查1个verifier |
| P：公开执行 | 干净提交上的根check.py或任务规定的公开入口 | 整题1个verifier |

完整性I作为独立硬门槛，不通过加入一个可被其他分数抵消的检查项实现。独立稳健性集合R不进入核心分母。

同一注册单元不能重复计分。公开检查可覆盖部分相同业务行为，但P仍只计1个单元；不再额外增加一个“严格通过verifier”。B内部的若干assert也不逐个增加Reward分母。

原14题等原生任务按其已有接口注册：没有transform契约时，不新增该函数要求；可保留原生模块检查于D；没有独立核心转换用例时，该项通过率为N/A。不得为了统一格式改变任务内容。已有等价根检查时，不重复增加P。

## 3. 完整性I

`integrity_ok`要求任务规定的受保护文件、契约、输入与检查在评测前后保持允许的内容及路径。检查脚本和期望结果由评测方保存，agent不能通过修改它们获得分数。

完整性失败时：`public_pass=false`、`strict_pass=false`、`reward=0`；未执行或不可信的转换结果不计入可信通过数。若保留原始诊断值，应单独标注为不可信，不能并入正式指标。

## 4. 公开通过

令P表示公开入口在规定时间内正常结束且退出码为0：

`public_pass = integrity_ok AND P`

- 在独立提交副本中运行，移除上次执行遗留的待生成产物后重新执行。
- 非零退出、候选程序异常、缺少入口或候选程序超时均为公开失败。
- 基础设施错误单列；不得将程序错误、预算耗尽或接口不完整当作基础设施问题剔除。
- 公开通过只说明公开验收入口成功，不替代隐藏用例或接口独立运行验收。

P必须进入核心清单，并同时成为严格通过的显式条件。不能只记录`root_execution_succeeded`却不让它影响严格结果。

## 5. 核心转换用例通过率

记核心转换用例总数为N_A，通过数为K_A：

`core_transform_case_pass_rate = K_A / N_A`

每个用例直接调用transform，并按任务既有契约检查结果、返回结构、应抛出的异常、输入不可变性与可序列化性。合法输入不能误拒绝，明确非法的业务输入应按约定拒绝。

这个分子、分母**不包含**load_payload、build_component、parser兼容性、公开执行、磁盘产物或可选稳健性。context8等适配器如果原先将parser一致性混入API探针，迁移时应将该归因移入B，并冻结迁移后的检查清单。

N_A=0时显示N/A，不能补成0%或100%。适用用例因候选程序崩溃、超时、缺实现或预算耗尽而未执行，仍保留在固定分母中并记失败。报告必须同时显示K_A/N_A和比例。

## 6. 接口独立运行与交付物重建

B按组件打包，内部所有适用检查通过才记该bundle通过：

1. load_payload按题目已有约定处理合法及非法输入，不增设任务未声明的格式要求。
2. build_component在新建临时根目录直接调用，仅提供合法输入及contract，目标产物事先不存在。
3. 至少覆盖两组不同合法输入，或沿用等价的既有冻结覆盖。新增验收用例必须显式列入新版本清单。
4. 对照评测方冻结的期望结果；不能只比较两个可能同时错误的候选函数。返回值、写文件副作用和路径关系按题目契约分别验收。
5. 需要parser的题目，在B中检查其兼容性，不能因此混淆核心转换通过率。

不能先跑命令行生成目标文件，再让build_component读取旧文件以证明它能独立工作。contract.json是输入数据；将它作为Python脚本执行不能替代按契约读取它。若契约允许缓存，仍须验证首次无缓存执行。

D同时要求从保留提交重新生成最终产物，并检查任务规定的内容与依赖一致性。函数返回正确不代表落盘产物正确；落盘文件正确也不代表函数接口能够独立调用。

B内部一个子检查失败，该组件B单元记0；其他独立通过的A、D、P单元仍可取得部分进展分。原始子检查数和bundle数分别记录，不能把“26/27个子检查”直接当作总Reward的分子和分母。

## 7. 整题严格通过与独立稳健性

`strict_pass = integrity_ok AND P AND all(A) AND all(B) AND all(D)`

任何一个适用核心条件失败，整题Strict Pass为0。集合不适用时不制造额外要求，但核心验收清单不能为空，公开入口P必须存在。

未知额外字段等与核心交付无关的通用稳健性，按具体版本注册为独立集合R，不扣核心Reward，不决定核心严格通过：

`full_spec_pass = strict_pass AND robustness_all_passed`

没有注册R时，`full_spec_pass`和稳健性结果显示N/A，不将“未评估”写成“已通过”。实际使用的业务字段有效性及已声明的JSON解析契约仍按核心规则验收。

历史六题v3的`strict_all_checks_passed`同时包含可选稳健性，更接近这里的`full_spec_pass`；不能未经版本说明就将它改作核心`strict_pass`。

## 8. 正式Reward：50%进展分＋50%完整交付奖

令：

- `V=A∪B∪D∪{P}`，N为已注册核心verifier总数，K为其中通过数。
- `p=K/N`，S为整题Strict Pass指示值。
- W为该发布版本预先冻结的Reward上限：E=1、M=2、H=3。
- I为完整性指示值，完整性通过为1，否则为0。

正式公式为：

\[
Reward = I\cdot W\left(0.5\frac{K}{N}+0.5S\right).
\]

其中：

`progress_reward = I × W × 0.5 × p`

`delivery_bonus = I × W × 0.5 × S`

`reward_raw = progress_reward + delivery_bonus`

规则：

- 分母固定；missing、timeout、exception均记失败，不从N移除。
- 只有核心严格通过才获得完整交付奖；仅公开通过或转换用例100%不能获得该奖。
- 完整性失败全部清零，不能用其他功能正确抵消。
- R独立报告，不增加也不减少上述核心Reward。
- 原始精度计算后，只对每题最终Reward执行六位小数`ROUND_HALF_UP`；不要先将p或两个分量舍入再相加。
- Strict Pass由冻结检查和布尔门槛判定，不能通过“显示分数等于满分”反推，避免舍入掩盖失败。
- 以六位单题Reward求和形成发布总分，并明确显示精度；保留K/N/W/S/I供复核。

这是“等权注册验收单元”，不是所有底层assert等权。拆分/合并检查、改变bundle内容或增加公开检查，都会改变p，必须版本化。

## 9. 示例

以下仅为合成计分例子，不代表实际某题的检查清单：

| 场景 | W | 核心K/N | S | Reward |
|---|---:|---:|---:|---:|
| 易题完成部分核心检查 | 1 | 3/4 | 0 | 0.375000 |
| 中等题仅一个核心单元失败 | 2 | 30/31 | 0 | 0.967742 |
| 难题接近完成、仍未严格通过 | 3 | 39/40 | 0 | 1.462500 |
| 中等题完整交付 | 2 | 31/31 | 1 | 2.000000 |
| 难题完整交付 | 3 | 40/40 | 1 | 3.000000 |
| 完整性失败 | 2 | 不接受为可信结果 | 0 | 0.000000 |

例如中等题有22个核心转换用例、3个接口bundle、5个产物/集成检查和1个公开检查，共31个单元。转换22/22全过，但一个接口bundle失败时，核心转换用例通过率为100%，Strict Pass为0，Reward为0.967742。若公开检查是唯一失败项，Reward相同，但`public_pass=false`。两类失败原因须分别展示。

若所有核心单元通过、仅独立稳健性失败，则Strict Pass仍为1、Reward仍为W，只有Full Spec Pass为0。

## 10. 难度权重与数据集汇总

W由任务发布前冻结的`reward_difficulty`决定，不随某个被测harness本轮的表现事后改变。结构难度、条件实测难度和Reward权重分别保存；不得用Reward倒推任务难度。

对于已有六题v3，历史M上限2继续保留。后续若调整权重，应发布新版本，并让全部比较对象在同一权重与任务集合下报告结果。

主汇总可以报告：

`reward_sum = Σ reward_t`

`difficulty_weighted_normalized_reward = Σ reward_t / Σ W_t`

同时附报按题等权的`mean(reward_t/W_t)`，以区分难度权重与完整交付奖励的作用。两者名称与分母必须明确，均不是Strict Pass Rate。

按历史冻结W计算，原14共14分、扩展16共48分、改编26共52分，56题总上限114。其任务版本、题目集合和权重不匹配时，不允许直接合并排名。

## 11. 统一结果字段与重复试验

建议至少输出：

| 字段 | 含义 |
|---|---|
| task_version / scoring_version / scoring_revision | 数据与评分协议版本 |
| checks_sha256 | 固定核心清单摘要 |
| integrity_ok / public_pass / strict_pass | 三个显式布尔结果 |
| core_transform_cases_passed / total | 仅核心转换用例计数 |
| core_transform_case_pass_rate | 核心转换用例通过率；不适用为null |
| interface_bundles_passed / total | 接口bundle计数，另保留子检查明细 |
| core_verifiers_passed / total | 计算p所用的固定分子分母 |
| reward_max / progress_reward / delivery_bonus / reward | 上限、两个未提前舍入分量和最终Reward |
| robustness_* / full_spec_pass | 独立稳健性及全规格完成结果 |

所有比例同时报告分子分母。旧`api_acc`只可作为带版本说明的兼容字段，不得展示成“全部API正确率”。

重复试验必须固定模型、模式、harness、预算、任务和验收版本。每题先对固定次数的有效尝试取均值，再按声明方式跨题汇总；不能将某个harness五次均值与其他harness一次结果伪称同一重复协议。

程序错误、接口不完整和预算耗尽保留为有效失败。基础设施故障单列并按既定规则处理；不得挑最高分恢复尝试。针对失败题追加的定向复测另列，不静默替换冻结主结果。

跨题的核心转换用例通过率以每题平均后等权汇总为主，另可附按用例数加权的micro值，并报告适用任务覆盖数。

## 12. 50%的依据与敏感性要求

[TheAgentCompany论文§4.1](https://arxiv.org/html/2412.14161v1#S4.SS1)采用50%检查点完成比例＋50%整题完成奖励，同时分别报告完整完成指标。这为本项目兼顾部分进展和完整交付提供了直接的方法先例。

本项目将其进展项具体化为冻结核心verifier通过比例，并额外使用发布前冻结的W；不能声称W=1/2/3或本项目验收清单也来自该论文。50%是规范性设计选择，不宣称已证明对所有任务最优。

正式报告应附至少20%、30%、50%的权重敏感性，按同一任务集合和冻结记录比较。可增加0%、70%、100%端点，披露局部任务集换位和接近分差的不确定性。不因某研究harness在某个占比下排名最高而事后选择权重。

## 13. 实施状态与迁移

**当前状态是规范采纳，评分器迁移待独立版本化；既有数据包的比例评分器仍按其原版本解释。** 不能仅把旧policy的占比改为0.5，就声称已补齐全部新版验收。

实施时必须：

1. 显式注册P，并使其约束Strict Pass；已有等价根检查不重复计分。
2. 分离transform与parser/加载/构建检查的归因，展示“核心转换用例通过率”。
3. 验证构建接口首次无缓存、不同合法输入和最终产物重建；不改变任务契约。
4. 冻结新评分器、清单、期望与摘要，并验证满分、部分分、公开失败、接口失败、完整性失败及仅可选稳健性失败的控制样例。
5. 保留历史分数和旧verifier，新增结果记录迁移版本和来源。

历史记录允许按此50%公式进行离线换算，但必须标记`legacy-reaggregation-50`：它使用旧版本p和S，只说明奖励权重改变的效果，不等价于候选通过了新增独立运行验收。若变更清单或Strict Pass定义，须对保留提交重跑新verifier；有模型新尝试时另列，不能把离线重评分计成新增运行。

机器可读定义见[reward-policy-v1.0.json](reward-policy-v1.0.json)，合成例子见[examples-v1.0.json](examples-v1.0.json)。
