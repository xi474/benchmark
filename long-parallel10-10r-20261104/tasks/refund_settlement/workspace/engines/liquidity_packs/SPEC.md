# liquidity_packs

All required fields below are mandatory (including empty lists/maps). IDs match [a-z][a-z0-9_]{0,15} exactly: do not strip, lowercase or coerce. Integers exclude bool. All integers are nonnegative unless explicitly stated otherwise. Reject NaN/Infinity anywhere, including extra fields. Reject missing fields, invalid types/ranges, duplicate IDs, unknown references and cyclic prerequisite graphs with ValueError, never leak KeyError. Record IDs are unique within their own list; different lists have separate namespaces. Extra fields may be ignored after finite-value validation. normalize returns a new canonical object containing only specified fields: record lists sorted by id, ID lists sorted and unique, nested effect/contents lists sorted by their reference key. No input or contract mutation. Both normalize(payload) and solve(payload, contract) independently accept and validate raw input. The contract object is file/API metadata, not business input. Use an exact algorithm for bounded input sizes. Return the bare result object with exactly the specified keys, types, ordering and tie rules; no name/result envelope.
audit.verify(payload, result, contract) must validate raw input and return a bool. For valid payload it must accept a correct result and reject malformed, infeasible or numerically inconsistent results. It must recompute feasibility and totals from input and the proposed decision, rather than unconditionally accepting, trusting totals, or simply delegating to solve. It need not prove global optimality: focused and final tests separately compare solve against exact optima. For invalid payload it raises ValueError; malformed result returns False. It must not mutate input/result/contract. All APIs use only the Python standard library.

Input {needs:[{id,quantity}],offers:[{id,contents:[{sku,quantity}],price,weight,carbon,limit,group}],max_spend,max_weight,max_carbon}; <=8 needs,9 offers; contents.quantity>=1; limit integer0..3; group empty-string or ID. Contents SKU references needs, unique per offer; normalize sorts contents by sku. Choose each offer count0..limit. Total spend,weight,carbon fit their bounds. For each nonempty group at most one distinct offer can have positive count (multiple purchases of that one offer allowed). Delivered quantities must meet every need. Overfill=sum(delivered-required) across all need IDs. Optimize minimum cost; minimum overfill; minimum carbon; minimum total purchase count; minimum full numeric count tuple in offer-ID order. Return {feasible,cost,weight,carbon,overfill,purchases:[{offer,count}],delivered:[{sku,quantity}]}; only positive purchases sorted by offer, delivered includes every need sorted by sku, including zeros. Infeasible false,0,0,0,0,[],[]. Empty needs feasible with empty purchases/delivered.

Required policy input is a root-level object policy {cash_buffer,settlement_fee}. Each policy value is an integer from 0 through 8 inclusive. The policy object follows the same extra-field rules. Normalize and validate the original input, retaining only the two required policy fields inside policy. Canonical normalization does not apply the policy. Apply the following rule exactly once to a separate working copy for solve and verify. Use the effective fields for every downstream feasibility check, objective, tie breaker and numeric result. Preserve all IDs and output keys.
Subtract cash_buffer from max_spend (floor 0). Add settlement_fee to each offer unit price when its contents list has more than one entry.
