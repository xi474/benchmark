# Global container retrieval with shared staging space and parallel cranes

This is a fictional finite stack-planning puzzle, not port operating guidance. Input is {containers,stacks,links,cranes,retrieval_groups}. containers has2–6 unique {id,hazard,appointment_tick,rehandle_cost,handling_ticks}; appointment_tick is a nonnegative integer, rehandle_cost and handling_ticks positive integers1..4. stacks has3–5 unique {id,capacity,allowed_hazards,containers}, capacity1..4, container IDs in BOTTOM-TO-TOP order. Initial capacities/hazards are valid and every container is on exactly one stack. links lists directed {from,to} allowed rehandles between DISTINCT stacks; moving backwards requires its own link. cranes has1–3 distinct {id,reaches}, reaches a set of valid stack IDs. retrieval_groups is an ordered list of nonempty container-ID sets partitioning ALL containers. All data is well formed and finite. Array order outside retrieval_groups and each stack's bottom-to-top contents has no action priority.

At any state, the CURRENT retrieval group is the earliest input group with at least one container still in the yard. Only its remaining containers can be retrieved now. Same-group targets may be processed in parallel. Future-group targets cannot be retrieved until a later wave after the current group is empty, but ANY top container (including a future target) may be rehandled to prepare space.

An operation is {crane,kind,container,from,to}. It takes the TOP container of source from. For kind:'rehandle', to is a different stack with a directed link from source, free capacity and the container's hazard in its allowed_hazards; its rehandle_cost is charged and it is pushed on top of to. For kind:'retrieve', to:null, the container must belong to the CURRENT group and the operation may START only at or after appointment_tick; it permanently leaves the yard and costs no rehandle charge. Both kinds take that container's handling_ticks. Appointment restrictions apply to retrieval only, not to preparatory rehandles.

A wave/batch is {start,operations} with at least one operation, at most one per crane. Each crane must reach EVERY stack touched by its operation: the source and, for a rehandle, the destination. Touched stack sets of DIFFERENT operations must be DISJOINT. Therefore one operation cannot consume another's newly exposed top or newly freed slot in the same wave; all preconditions read the wave's PRESTATE. Source/destination exclusivity applies even when different cranes could reach the same stack. All operations start simultaneously. Their individual completion ticks are start+handling_ticks, but the next wave cannot start until start+MAX(handling_ticks) of this wave. Current-group eligibility is also evaluated before the wave; finishing a group inside the wave does not permit a future-group operation in that same wave. Output operation order is immaterial.

The first wave starts at integer time>=0, later starts are integer and at least the previous wave finish. Waiting is allowed, including for appointments; there are NO deadlines, holding charges or real-time services. Cranes have fixed reach sets and no persistent position/travel state. Containers may be rehandled multiple times, subject to capacity/hazard/direction rules each time. Do not restrict rehandles to blockers of the next requested target: strategic relocation can be necessary.

Retrieve ALL containers, optimizing lexicographically: FIRST minimize total rehandle_cost across the entire plan; THEN minimize finish_time, the end of its final wave. Accept ANY globally optimal legal plan and any legal crane matching. There is no ID, destination-height, minimum-operation-count or earliest individual delivery tie-break. Choosing a temporary stack greedily can occupy the only space a later blocker needs.

Return exactly {status,rehandle_cost,finish_time,batches,delivered,stacks}. For status:'ready', batches is the complete plan; delivered contains exactly one {container,tick} for each container at its ACTUAL operation-completion tick, and stacks contains every {stack,containers} final bottom-to-top state (all empty). rehandle_cost and finish_time must match the actual plan and the global optimum. If impossible, status:'infeasible',rehandle_cost:null,finish_time:null,batches:[],delivered:[],stacks equal the INITIAL stack contents. Stack/delivery/list/map order is immaterial except the time order of batches. The verifier replays YOUR plan rather than requiring the reference sequence.

Public example: all costs/durations1, appointments0. left has bottom A,top B; right has bottom C,top D; a and z are empty capacity1 stacks, left/right capacity2, hazards all compatible. Links left->a,left->z,right->a,a->z. Two cranes both reach all stacks. retrieval_groups=[[A],[C],[B,D]]. The optimal rehandle cost is2: B left->z; D right->a. Four waves suffice: (1) move B to z; (2) retrieve A and rehandle D to a in parallel; (3) retrieve C; (4) retrieve B and D in parallel. All starts0,1,2,3 respectively, finish_time4. With one crane minimum finish6. Greedily putting B on the smaller-ID empty stack a requires another B move a->z before D can leave right, costing3 rehandles.
