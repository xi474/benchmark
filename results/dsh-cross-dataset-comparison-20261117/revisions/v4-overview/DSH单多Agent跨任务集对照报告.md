# DSH 单 Agent／委派策略跨任务集对照报告

**同事审阅v4导读版：2026-11-17（北京时间）｜数据仍为2026-11-15—17已登记结果及8次补充｜本次只修订说明，新增模型请求0。**

这份报告先解释每组实验为什么做、怎么做，再给出结论，最后展开表格、图表和trace证据。所有比较都使用DSH，任务来源和委派办法不同。

## 先用通俗的话说明：我们到底做了什么

我们想回答的是：**同一个模型做同一道任务时，让它一个人完成，和让它找子Agent帮忙，哪种更准确、更快、更省tokens和费用？如果开放委派，它会不会自己使用？** 因此，我们既看答案得分，也检查原生trace中有没有真实子会话、子是否工作、父是否收到结果，以及父子工作是否重叠。创建了子Agent，不自动等于获得了并行收益。

这里实际运行的Harness始终是DSH / Agent Team，模型始终是DeepSeek V4 Pro普通模式。我们更换的是任务来源和委派办法，不是在这份报告里比较五套Harness。LATTE、Mabench/τ-bench在这里指任务来源；R3指参考分工实验的第三轮及后续修复补跑；Complex10指同事提供的十道复杂编码题。后文S表示严格单Agent，N表示不追加委派提醒的原生组；M只是该研究中的委派条件代号，具体约束各不相同。

### 做了哪五类实验，各自想回答什么

1. **自有benchmark三题的“主算法＋独立验证”对照（R3）。** 使用E112、M103、L114三道题，每题原计划两次配对；每对让S和M各做一次。S自己实现主算法和参考验证，M由父实现主算法、固定一名子做独立参考验证，双方都承担同一套32例附加参考工作。目的：在分工已明确、工作量尽量匹配时，检查把验证分出去是否改善质量或缩短时间。L114原结果存在缺分或参考流程异常，后来对两个原重复分别做了整对重测，故下文按修复版本分列。
2. **LATTE原始模块扩展／调试任务对照。** 选模块扩展和调试两道原题，每题S/M各做三次，共12次。M按预先规定的分区创建两名子，父完成自己的部分并整合；S自己完成相同分区。目的：看看较适合代码分块或独立诊断的任务，能否从实际协作中受益。执行这些任务的是DSH，不是LATTE Harness。
3. **Mabench原两道零售任务的强制两子对照。** 使用原任务索引0和2，正式主对照为每题S/M各一次，共4次。M固定两名只读调查子，父负责与模拟用户交互以及业务状态写入，运行时检查点要求子先实际工作、回传后再进入相关后续操作。目的：先证明这条客户服务链路能真正用上子Agent，再观察调查并行是否抵消协调成本。早期8次不同条件的探索仅保留审计，不作为这4次的重复样本。
4. **Mabench多需求零售任务的可选委派对照。** 使用原任务索引20、23、41，各做两次S/M配对，共12次。M收到“评估值得委派的机会”的鼓励，但**允许模型自己决定是否委派，不强制子 Agent 数量**，0至3名都合法。目的：公开多个需求后，模型是否会自行识别值得拆分的调查工作；这与强制创建两子是两种不同干预。
5. **Complex10复杂编码题的三组对照。** 十道题，每题三个重复，分别设置N原生、S严格单Agent、M显式至少一名实际工作子；当前主分析选定30个完整三条件配对，共90次。M必须委派，但何时委派、如何分工、是否追加子由模型判断。目的：同时回答“原生是否主动委派”和“要求实际使用子Agent后，质量、时间和用量怎样变化”。本组没有单独的仅鼓励组。

### 各类实验目前得到什么结论

1. **R3：真实分工发生了，但没有稳定加速。** 选定六对的核心API合计为S71/72、M72/72，属于带版本说明的事后质量敏感性视图。L114配对重测A两组均12/12，E2E为884.5→412.6秒；配对重测B同样均12/12，却是510.0→754.5秒。一次多Agent更快，一次更慢；两对参考冻结机制和实际运行负载不同，时间、tokens、费用分开报告，不能拼成同一协议的重复均值。
2. **LATTE任务：功能检查改善，整题成功和资源效率没有同步改善。** 功能通过率按两题等权平均为87.33%→91.33%，整题成功均为3/6；M六次均实际创建两子，但平均完整E2E增加28.21%、tokens增加132.72%、冻结峰价费用估算增加132.43%。说明“多过几个功能检查”和“整题成功／更省资源”是不同结论。
3. **Mabench强制两子：能完成实际协作，但这两题没有展示净效率提升。** S/M正式两次均成功，M各有两名实际工作的子；M耗时、tokens和费用更高。样本每组只有两次，不能据此推广为所有客户服务任务都不适合委派。
4. **Mabench多需求可选：没有触发实际协作，不能据此评价协作收益。** 六次M均0子、0次spawn，工具和提示已核验可用；成功数为S3/6、M2/6。这是在比较两种提示／能力配置，不能把得分下降归因于子Agent协作，因为没有子Agent实际参与，也不能无证据地说模型已正确判断“不值得委派”。
5. **Complex10：平均时间改善，准确率与成本没有同步改善。** 原生N有12/30次自主创建子Agent，S为0/30，M为30/30。S/M功能断言为29600/29727→29543/29727，整题成功22/30→21/30；M平均完整E2E减少12.77%，但tokens增加4.46%、冻结峰价费用估算增加26.88%。这是当前任务组合上的观察，不能概括成“多Agent全面更好”。

**共同结论：DSH确实能够创建、执行和接收子Agent结果；是否值得委派取决于具体任务、分工及执行路径，目前没有稳定的“准确率、E2E、tokens、费用四项同时改善”。** 五类研究的委派约束不同，不应把它们合并成只改变Agent数量的一个统一因果实验。

## 1. 任务来源、运行模式和预算：先区分配置，再看结果

实际执行者始终是 **DSH / Agent Team 0.2.1-rc.2**，模型固定 **DeepSeek V4 Pro普通模式，出口`thinking.type=disabled`，单次响应上限32768**。本报告没有用LATTE或LangGraph Harness执行这些任务。LATTE指模块扩展/调试两道任务的来源；Mabench/τ-bench指固定Mabench实现中的retail任务、业务API、模拟用户和原评分器，不称为“LangGraph论文系统效果”。Complex10是同事提供的7+3道复杂编码任务；R3是E112/M103/L114参考分工系列的第三轮及后续整对补充。

**“自由选择时机”不等于“可以选择不创建”**：Complex10的M可以自选时机和分工，但实验指令仍强制至少1名工作子；Mabench多需求M则**允许模型自己决定是否委派，不强制子 Agent 数量**，0子本身就是合法结果。Mabench可选组有鼓励性提示，因此也不能称为完全不加干预的原生组。Complex10没有额外的“仅鼓励委派”组，主表S→M比较的是严格单Agent与至少一子条件；原生N另列。强制表示实验规定必须委派，并非宿主替模型自动创建；真实子会话仍须由模型调用原生工具建立。

Complex10的最低一子要求来自提示与事后工作/回传验收，未加载强制在特定工具前创建子的检查点；Mabench原0/2题则确有这种运行时前置门禁，二者不能混称为相同的强制方式。子ID总数是跨试次累计创建数量，不是同一时刻并发成员数；至少一子实际工作/回传的按试次验收，也不意味着每一个累计创建ID都成功完成了同等工作。

## 8. 当前可以和不能得出的结论
