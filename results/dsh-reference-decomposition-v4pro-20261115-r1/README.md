## 为什么不是干净的净收益对照

1. **研究快照漏带公开runtime.py，是本地比较驱动问题。** 原始engine保留`from runtime import build, read`时，快照只打包engine/contract/parent_impl，导致32例附加比较出现ImportError。原驱动还只回传stderr，吞掉了stdout中的结构化错误。离线从7个试次的8个保留快照重现；仅补入原冻结seed中的runtime.py后，8/8公开首例恢复执行，修订发布流程32/32回归通过。修订版仅离线保存，未替换原驱动、成绩、账本或E2E。正式verifier未修改，该缺陷主要污染额外参考比较的反馈与修复负担。
2. **相同版本不等于相同故障剂量。** 不是每个模型API请求都出错：4次在进入参考比较前即协议中止，有些实现保留runtime导入而持续失败，有些为绕过缺依赖重写接口，有些继续修复算法。固定同一有缺陷的pipeline，可以回答该配置下的系统表现；但不能把差异单独归因于多Agent或认为共同缺陷已自动抵消。
3. **5次强制记录协议未完成。** 多数是evidence_refs没有严格取自当前runtime签发的refs数组；模型有时引用了其他真实读取或旧检查点ID。这是模型遵从与过窄协议接口共同形成的失败，不等同DSH算法能力不足。4次很早结束，另1次L114 S第二次虽API12/12仍协议未完成。快失败绝不是单Agent加速收益。
4. **评分排队显著不同。** L114 r1 M的Agent阶段约385.0秒，完整E2E1344.6秒，其中等待单Verifier分配916.2秒；S的Agent阶段335.7秒、E2E646.6秒、分配等待约0。完整E2E必须保留，另列排队才能解释原因。M在Agent阶段也未比S更快，且API从S12/12降至M0/12，暂未见质量保持的净收益。
5. **参考正确不等于主实现正确，也不等于验证完整。** M的4个参考目标均32/32正确，L114 M首轮研究32例也全部通过，但正式API0/12，说明这32个小域输入及见证检查不能覆盖正式任务所有情况。S E112 r1自编参考仅29/32正确；S M103 r2参考只成功计算11/32。原wrapper的reference_workload_completed只是粗略流程标记，最终必须看每轮attempted/compared/passed，不得把它直接解释成32例有效比较。
6. **比较后产物可能再变化。** 有些最后发布快照与最后实际比较的快照不同；S L114 r1交付代码还与最后发布快照不同。只能对特定内容哈希的候选解释研究比较，不能移植到另一份最终代码。
7. **重复次数与资源制度有限。** 每题每组仅2次，S/M因pilot门禁不同步入场，缓存与Verifier排队不同。四Harbor/共享HTTP4的结果是这个资源制度下的探索，不能外推为隔离纯并行加速或所有任务不需拆解。
