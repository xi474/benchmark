# 显式委派与原生未触发组：API 准确率回退的 trace 归因

分析日期：2026-11-13。对象为本轮 Nanobot、OpenCode、Codex、DSH，各原 Medium26 保留的 Medium20 加 adapted6-core-v3 六题。LATTE、LangGraph 不在此次显式委派对照中。本分析只读取已经结束的试次，没有调用模型、重跑题目或修改数据集／verifier。

## 结论

不能概括成“multiagent 一定降低 acc”。Medium20 中 Nanobot、DSH 略降，Codex 的明显下降集中于两次输出上限异常，OpenCode 反而上升。修订六题中三套上升、Codex 持平。

目前证据支持的主要原因有两层：

1. **Codex 的主要净损失来自预算／实际推理模式问题。** MP20、MP22 两个显式组试次达到单次输出 32,768 上限，原生 CLI 报 `max_output_tokens` 并结束，合计损失 58 个原本通过的 API 检查。其中 MP22 根本没有创建子 Agent。这不能当作多 Agent 协作使代码质量下降的证据。
2. **正常完成试次的主要回退来自公共输入约束和接口细节没有贯穿分工及最终验收。** 父 Agent 分配业务实现、通用 model/render、编排等工作后，部分子实现只在 JSON 文件读取时校验，直接调用 `transform()` 的路径遗漏校验；也有金额、文本拼接等输出规范错误。父子确实做过局部检查，但检查主要证明流程自洽，未覆盖这些语义边界。

没有足够证据把下降主要归因于文件并发覆盖、结果完全未回传，或者“子 Agent 天生能力更弱”。这些是可能的机制，不能代替已观测证据。

## 配对方法与可比范围

- 104 对题位，208 个选定有分结果；每对按 Harness、数据集、题号配对，并逐项对齐同一 `api/` 检查 ID，共 2,592 个检查位。每个选定结果的 result/score SHA256 复核通过。
- acc 指 **API 检查通过数／API 检查总数的微平均**，不是任务满分率、总 reward 或交付检查通过率。下表的百分点变化直接由整数分子、分母计算。
- 原生组是历史上未观测到子 Agent 的默认执行，不是禁止委派的单 Agent 消融。显式组是提示条件，部分异常试次还未产生真实协作；不能把“显式提示”直接等同于“完成多 Agent 协作”。
- R7 三个 Codex 补跑只替换本分析的无分占位，不覆盖旧失败 attempt；它们以 `r7-repaired-chat-disabled` 单独标注。R7 与旧 Responses 适配不可当作严格同适配控制变量。
- Medium20 两组冻结题目中，除预装镜像 Dockerfile 外，共 1,573 个文件逐字节核对一致，无缺失或差异。此结果排除了本次 Medium20 配对的题面／verifier 文件漂移，**不等于已证明所有规格无歧义**。
- 历史原生与显式执行不是随机重复实验。旧 Codex 请求 `reasoning.effort=none`，但原生日志有非空推理内容，实际普通模式仍存在疑点；不作严格普通模式排名或统计因果结论。R7 三题真实 Chat 出口为 `thinking.disabled`，不把旧有分行重新标为已验证普通模式。

## 主要原因一：Codex 的两次输出上限中止，解释全部净下降

| 题目 | 原生 API | 显式 API | 实际子 Agent | 原生终态证据 |
|---|---:|---:|---:|---|
| MP20 | 29/29 | 0/29 | 创建 2 个 | CLI turn.failed，max_output_tokens |
| MP22 | 29/31 | 0/31 | 0 个 | CLI turn.failed，max_output_tokens |

两题最后一个已结算响应的 output tokens 均为 32,768；其中 reasoning tokens 分别为 30,142 和 32,768，占该响应输出预算约 92.0% 和 100%。这是**最后一个响应**的占比，不是整题 token 比例。旧请求虽指定 none，实际原生推理内容与模式审计有疑点。

MP20 的两个子身份虽已创建，但在根进程异常时被取消，未见其工具执行；其自身模型工作在这份证据中仍不能统一确定，不填成零。MP22 没有创建子 Agent，已经足以否定“这两题都是多个子 Agent 互相干扰导致”的解释。

逐项核算：两题贡献 58 个毛回退；Codex 全部 Medium20 有 68 个毛回退、10 个改进，净少 58 个。其余正常完成题的退化是 MP05 少 4、MP16 少 3、MP25 少 3，同时另有 10 个检查改善，净变化抵消。

仅作原因分解，暂不计这两个显式输出上限试次后：

- 最新选定的其余 18 题，两组均为 **389/446**。
- 为避免混入 R7，进一步仅看旧适配匹配的 17 题：原生 389/436、显式 331/436；同样暂不计这两题后，其余 15 题均为 **331/376**。

这不是剔除差结果后的新正式成绩，原来的输出上限结果仍保留在正式汇总中。它说明的是：**本轮 Codex 的净下降可以由两个预算异常题完整核算出来，尚不能据此证明完成协作后的平均代码质量下降。**

最新 R7 的 MP15、MP17、MP19 合计 API **58/70**，与历史原生对照不仅总数相同，连每个检查 ID 的通过／失败位也完全相同。它们是有部分错误的结果，但不是相对普通执行新增的错误。早期 HTTP／工具历史转换失败均保留为基础设施异常，不以 reward 0 混入本次质量比较。

## 主要原因二：分工完成了业务代码，公共校验却没有覆盖直接 API

Medium20 的毛回退中：

- Nanobot：40 个回退里 28 个是 robustness，约 **70%**；其中非法顶层输入 19 个、额外字段中的非有限数 9 个。
- DSH：26 个回退里 15 个是 robustness，约 **57.7%**；非法顶层输入 8 个、非有限数 7 个。
- Codex 除两次输出上限外，正常完成题的 10 个回退中有 7 个是额外字段非有限数校验，另 3 个为金额字符串格式。

这些规则已出现在被测 Agent 实际读取的 README 中：必需字段缺失／指定错误类型应为 `ValueError`；未知额外字段可以忽略，但其中的非有限 JSON 仍非法。不是本分析临时增加的新要求。

### 代表案例：Nanobot MP26，34/36 → 26/36

父 Agent 将工作切为三个真实子身份：通用 model/render、五个业务 transform、run_all/final_report。业务实现者收到一份统一 transform 模板：核对输入数量，unwrap，调用 `_compute`，返回封装。

`evt-000151-a18d8183` 的委派模板和实际日期组件写入 `evt-000318-2e9cff55` 一致：有 payload 数量检查，没有在 `transform()` 入口验证每个业务输入对象，也没有对整个输入递归排除非有限数。文件读取器虽有严格 JSON 解析，它只保护从文件进入的那条路径。

正式 API 探针直接调用 `transform(payloads, contract)`，不经过 `model.load_payload()`。因此缺失的入口校验暴露为两类错误：应报 `ValueError` 时抛其他异常；或者额外字段含非有限数时仍正常返回。

该题新增的 **8 个失败全部是这两类 robustness 检查**：五个组件的非法顶层输入，以及 plan、notifications、apply 的非有限额外字段。原生实现对应位置有更多直接入口校验，例如日期组件会先检查业务输入对象类型。

这里有较强的“分工 → 共用模板遗漏 → 多组件同类失败”证据。但不能由此声称子 Agent 看不到 README：文件在其可读范围，部分子 Agent 也实际读取过；问题是规则未落实到所有 API 路径及父验收。

### 代表案例：DSH MP26，33/36 → 28/36

实际有两个队友：calendar-engineer 负责 dates/calendar，plan-engineer 负责 plan/notifications/apply。父 Agent 提供通用 model.py；plan 工作者完成三个业务组件并回报 `MODULE_OK`。

新出现的 6 个失败恰好落在 **plan、notifications、apply × 非法顶层／非有限额外字段**，同一工作包里的公共约束重复遗漏。另有 1 个检查改善，所以净少通过 5 个，而不是 6 个。

这一对应关系比“多了子 Agent 所以不稳定”具体得多：公共输入合法性没有作为业务实现者和父 Agent 最终验收的共同责任。不能仅凭分组对应断言它是唯一原因，代码与评分是直接证据，工作包设计与回退的联系属于有证据支持的机制解释。

评分中的 `actual_keys=[kind,type,message]`、`expected_keys=[kind]` 是 probe 对“非 ValueError 异常”和“ValueError”的包装差异，**不是候选 API 返回了多余的错误 JSON 字段**。本分析已核对 probe 源码，避免误判。

## 主要原因三：局部成功没有变成独立、充分的集成验收

这不是“没有自检”。在上述 trace 中，可以看到子任务局部测试、结果回传，以及父 Agent 再次执行完整检查：

- DSH MP26：子检查 `evt-000197-582f4e43`，返回 `evt-000198-c151a457`；父检查 `evt-000357-f95a13d0` 和 `evt-000372-4ae0d6bf` 均收到 `LOCAL_CHECKS_PASSED`。
- Nanobot MP26：`evt-000465-4083c247`／`evt-000533-dfe5e253` 的执行结果包含五个 `MODULE_OK`。
- Nanobot MP22：`evt-000312-0c12bdb3`／`evt-000344-b5626461` 的执行结果包含五个 `MODULE_OK`。

冻结检查器源码表明，`check_module.py` 主要在公开输入上比较 transform、build_component 与输出文件是否一致，检查封装和输入未被修改；`check.py` 运行编排、结构与最终报告检查。它自己也明确输出“external verifier determines official correctness”。**相同错误被 transform 与文件输出共同实现时，这种自洽检查仍然可以通过。**

所以观察到的流程是：分工实现 → 子 Agent 本地 smoke 通过 → 父 Agent 整体 smoke 通过 → 正式 API 边界仍失败。缺的是针对公共契约的独立边界审查，不是子结果完全没有发回来。

DSH 导入事件编号反映日志拼接顺序，不能据编号推出父子执行先后；本报告引用编号定位证据，不用它估算工具并行时间。Codex 也缺统一可比较的工具进程时钟，不能把日志接收时刻当真实执行时刻。

## 其他回退：格式与接口收窄，需区分代码错误和规格歧义

### Nanobot MP22：25/31 → 13/31

共 12 个新增失败：4 个 robustness，8 个业务文本输出。业务子 Agent 实现的 `_join_ab()` 使用 `"".join(parts)`，例如输出 `New Org.Dept.`，冻结 verifier 预期 `New Org. Dept.`；另一组是标题 `Example :subtitle` 与 `Example : subtitle` 的差异。原生组对应检查通过。

代码差异与 8 个失败的输出差异吻合；父最终 smoke 未拦截。这是能定位到函数的格式回退。不过公开说明使用“连接、空白折叠”等措辞，未在该句明示分隔符，因此**不能单凭这个案例证明是委派压缩导致规则丢失，更不能排除规格表达不够明确的影响**。评分保持原样，分析单列这种不确定性。

### DSH MP03：15/29 → 11/29

4 个新增失败都在 merged 组件的合法输入上。父 Agent 在 `evt-000293-0a4d943e` 中要求记录中的 options 为字符串；子实现 `evt-000071-b972aa27` 对其逐项检查 `isinstance(..., str)`。冻结参考解析器却产生排序去重后的 **options 列表**，因此独立 merged 探针被候选以 ValueError 拒绝。

该题公开说明是“options:逗号分割去重排序”，没有用明确 schema 写出列表类型。它揭示了**父子对同一错误接口假设达成一致，内部联调通过、独立组件 API 却失败**的机制，也暴露规格类型表达的歧义；不将这 4 个回退全部认定为纯粹的 multiagent 协作缺陷。原生有些解析失败是两组共同错误，不重复算成本轮新增下降。

### Codex 正常完成题：MP05、MP16、MP25

MP05 的 4 个回退和 MP16 的 3 个回退均是非有限额外字段未拒绝，与公共校验只在部分路径落实的问题一致。MP25 的 3 个回退是金额规范化：候选返回 `1,200.50`，冻结评分要求 `1200.50`；实际 amounts 代码 `_parse_amount()` 将匹配到的整数部分直接拼接小数部分，保留了逗号。定位证据为 `evt-000036-0091dea6`。这些说明正常协作仍会引入具体代码错误，但全体正常题也有同量改进，不能只报退化案例。

## 为什么“更多 Agent／更多 tokens”没保证更高 acc

Medium20 平均总 tokens 相对原生组，Nanobot 约 +16.4%、OpenCode +85.5%、Codex +38.9%、DSH +14.9%。这些包含实现、沟通、检查、重做等全部模型工作，不能直接叫“纯协调开销”。

Medium20 没有新增加累计 token 总门槛，因此不能用“多 Agent 抢光整题固定总预算”解释所有正常任务的回退。实际发生的是：有些 Codex 响应耗尽单次输出预算；一些正常任务的新增投入用于分配和重复实现，公共约束和独立验收仍不足。OpenCode 同时出现显著提升，进一步说明额外协作投入并非必然无效。

本次深查的文件写入通常有明确分工，尚无足够证据认定并发覆盖是主要下降来源。HTTP 共享限流可能拉长等待时间，但没有对应超时／取消链证据时，不能把它直接写成 API 正确率下降原因。监控缺失一律保留未知。

## 建议的下一轮控制变量（只提出，不启动）

1. 同题、同实际出口模式、同适配版本、同限额做重复配对；保留预算异常与基础设施异常分层。旧 Codex 模式疑点要先解决，不能只看请求字段写了 none。
2. 保留原业务任务与 verifier。委派包携带完整公共契约和写入范围，明确谁负责直接 API 的类型／非有限数／封装校验，谁负责跨组件接口；不能仅分配文件清单。
3. 将“实现者完成”与“独立验收”分开。父 Agent 或独立 reviewer 基于**公开规格**检查非法输入、原始／封装输入、业务边界和精确格式；不能把本次查看到的隐藏检查向量复制到后续被测提示中。
4. 若新增以上验收提示，标成新的实验条件；不可修改旧分数或把改进后的提示组混成旧显式组。先在一个 included pilot 验证监控，再按用户授权扩展。

现阶段最适合向导师陈述的是：**本轮观察到显式委派的收益不稳定；Codex 的主要下降是预算／模式异常，Nanobot 与 DSH 的正常任务回退主要表现为公共契约和接口验收不足。trace 支持这些具体失败机制，还不足以证明 multiagent 本身降低能力。**
