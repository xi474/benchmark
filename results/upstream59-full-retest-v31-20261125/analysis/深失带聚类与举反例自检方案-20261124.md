# 深失带 18 题问题聚类 与「分支完成前举反例自检」可行性方案（2026-11-24）

数据源：`review.json` 逐题 failed_checks（selected 基线）+ k-means 失败画像聚类 + 11-24 凌晨的 C 系 trace 分析。

## 一、问题聚类：4 个集群

### 集群 0：公开层崩坏 + 领域语义全崩（4 题）——最重
**C011、C033、C039、MS11**（缺口 12–15，A 通过率 0–10%，其中 3 题连 P 公开检查都挂）

- 特征：9–13 个具名语义用例失败 + B/solution 连带 + cli-artifact + 公开挂
- 根因（凌晨 trace 分析已验证）：实体识别/ELF-MIPS/因果图学习等**领域专业知识缺口**——模型对任务根本不懂，不是"差一个边界"。
- 与凌晨结论一致：A=0% 的题自检完全不可行（无法为不理解的东西生成正确期望）。

### 集群 1：领域语义部分理解（7 题）
**C049、C058、C066、MS14、MS28、MS41、MS42**（缺口 6–10，A 率 12–67%）

- 特征：具名语义用例失败 4–8 个，公开层能过（除 C011 外 P 全过）。
- 梯度：MS42(67%)/MS28(60%)/C066(50%) 是"半懂"；MS41(45%)/MS14(30%) 部分懂；C049(12%)/C058(11%) 接近概念错误。
- 根因：主框架对但细节语义错（如 MS41 每轮抽环境 vs 每票抽环境、MS02 字典序方向这类"读漏一句"）。

### 集群 2：工程工件链（1 题）——最轻
**N17**（缺口 6，A 率 89%）

- 特征：A 只差 1，失败主体是 D 链（template_dependencies/reverse_index/stylesheet_updates/final_report）+ B 连带。
- 根因：业务逻辑基本对，交付工件工程问题。**全深失带唯一非 A 主导题**。

### 集群 3：MP 边界遗漏 + 工件链连锁（6 题）
**MP01、MP06、MP07、MP15、MP20、MP21**（缺口 7–13，A 率 50–86%）

- 特征：A 失败全是 `heldout-XXX` 引擎边界用例 + `io/<engine>` 接口 + `output/*` 三连链（连锁性，随 A 自愈）。
- 根因：**规则在题面文本中、实现时遗漏了边界**（注意力缺失型，非知识缺失型）——这是凌晨 7 题近失带分析的同一模式。

## 二、「分支完成前举反例自检」可行性：分集群判定

核心机制：语义分支（组件/引擎）写完代码后、**返回合并前**，LLM 在分支隔离工作区内：抽取规则 → 生成对抗输入（反例）+ 从题面原文引用的期望 → 执行验证 → 命中即局部修复（apply_patch）→ 同反例复验（≤N 轮）→ 合并。

| 集群 | 题数 | 可行性 | 依据 |
| --- | --- | --- | --- |
| 集群 2（N17） | 1 | ✅ **高** | 业务逻辑基本对，反例可击中剩余边界 + 工件链 |
| 集群 3（MP 6 题） | 6 | ✅ **高** | 失败全是 heldout 边界，规则可从题面判定；**v5 自举循环已在 MP19 用"举反例+修复"翻正（22/22）**，是现成范式证据 |
| 集群 1（半懂 7 题） | 7 | ⚠️ **部分** | MS42/MS28/C066（A 率 ≥50%）可行；MS14/MS41（30–45%）勉强；C049/C058（11–12%）概念错误会传染到反例期望（相关性错误），不可行 |
| 集群 0（全崩 4 题） | 4 | ❌ **不可行** | A 0–10% + 公开挂：模型无法为自己不理解的东西生成正确期望；反例期望同样错，自检必然"绿" |

**净结论：18 题里约 7–10 题适合举反例自检（集群 2+3 全部、集群 1 的 3 题），8 题需要别的路线（thinking 臂/领域增强/独立验证）。**

## 三、机制设计（吸取 v5–v8 全部教训）

1. **时机在分支内、上下文热**：v5 教训——交付后独立 episode 自检成本 +142% 输入 token；分支刚写完代码时自检，边际成本 ~50k token（v6 实测）。
2. **反例必须"引用锚定"**：每个反例的期望必须附任务文本原文引用（哪一行推出什么结果）。这是对"相关性错误"（代码与测试期望同源同错）的最小抑制——引用不了期望的反例直接丢弃，不硬造（v6 教训：强制聚焦、自评不可靠 → 0/7）。
3. **反例要成组、要真跑、要修**：v5 成功靠"3 轮 × 5-10 个测试"的广度覆盖 + 修复循环；v6 的"1 次聚焦 1 个测试"命中不了实际 bug。每组件 3–5 条规则 × 3 反例起步。
4. **命中才修，修完同反例复验**：v8 教训——模糊指令会让 agent 改错方向（MP24/MS02 双回退）；反例本身给出可复现失败，修复有明确靶点。
5. **无命中直接合并，不设最低测试数**：避免 v6 式"为了自检而自检"。
6. **与默认配置叠加**：分支工作区隔离（ON 臂已提供）+ B 臂硬门（write_file 拒覆盖）+ shell 写审计（防绕道）→ 自检期间的修复天然走 apply_patch 最小改动路径。
7. **与"独立语义验证"的分工**：本方案是**启发式**（同一 LLM 自检刚写的代码，便宜、分支内、可常态开）；协作者方案①独立验证是**严格式**（封存期望、独立推导，重但防相关性错误）。建议：集群 2+3 常态开举反例自检；集群 1 半懂题用举反例做初筛、命中率低的升级独立验证；集群 0 直接上 thinking 臂。

## 四、建议试点

- **第一批（验证机制）**：N17 + MP15 + MP21（A 率 75–89%，反例最容易命中）——预期低成本翻正。
- **第二批**：MS42/MS28/C066（半懂但反例可达）。
- **对照**：集群 0 抽 1 题（如 C039）跑同机制，预期 0 命中——作为"反例自检对领域盲区无效"的负对照证据。
- 实现挂点：`agent_runtime_demo` 的组件分支返回前（dynamic_frontier/parallel_runtime_v2 的 merge 前钩子），新增 `branch_counterexample_gate` 模块；先做 prompt-only 版（复用现有工具：read_file + apply_patch + shell 跑组件），不新造工具。
