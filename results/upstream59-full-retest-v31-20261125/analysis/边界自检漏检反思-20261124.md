# 边界自检漏检反思：MP15 / MP21 为何没查出边界问题（2026-11-24）

v19 反例自检门控在 N17 翻正（11/17→17/17 strict ✓），但 MP15（25→23）与 MP21（17→17）的 heldout 边界问题全部漏检。用协作者诊断包（`MP-diagnostic-probes.json`）与 v19 turns 证据复盘后，定位到两个**不同的结构死穴**。

## 一、实证：隐藏边界 vs 模型自检的差距

### MP15（analysis 引擎）：覆盖盲区
- 隐藏失败（heldout-101/202/303 + io/output 链）全部同一 diff：
  `$.value.result.imports[3].module`：期望 `"typing"`，实际 `"typing.List"`。
- 语义：`from typing import List` 时，`imports[].module` 必须记**基础模块名**，不是限定名。
- 模型实际行为：61 个测试文件主要测 comments/ordinary 引擎的「排除注解/字符串」等**语义规则**——根本没把 `imports[].module` 字段格式当成规则。**自检再勤也查不到它没注意到的规则。**

### MP21（query 引擎）：推导被领域知识污染
- 隐藏失败（heldout-101/202/303 + empty-collection）全部同一 diff：
  `$.value.result.sql`：期望 `track_count GE ? AND name NE ?`，实际 `track_count >= ? AND name != ?`。
- 模型引对了规则（"op仅eq/ne/gt/ge/lt/le"），但生成期望时把 `ge/ne` **翻译成了 SQL 符号**——因为「SQL 本来就该用 >=」。**引用锚定拦住了编造规则，但没拦住推导时的领域污染。**

## 二、两个结构死穴

| 失败模式 | 本质 | v1 判定规则的漏洞 |
| --- | --- | --- |
| MP15 覆盖盲区 | 自由抽取规则 → 漏掉出题人设的**字段级约定** | R4 只限数量，未要求**输出 schema 逐字段必测** |
| MP21 推导污染 | 引文正确，但期望推导时**外部常识覆盖题面记号** | C1 要求引用推导，但未要求**记号与引文字面一致、禁止翻译** |

共同根因：heldout 用例是出题人针对「模型注意力和推导纪律」设计的陷阱；自检是**自我出题**，题目质量上限 = 模型的注意力与纪律。一题栽在注意力（没看见字段规则），一题栽在纪律（看见了但推导时改了）。

## 三、提示词 v2 修正（三个增量）

1. **输出 schema 逐字段规则**（堵 MP15 型）：contract.json / 题面声明的**每个输出字段**（字段名、类型、记号约定）必须各有一条规则——不再自由抽取。
2. **记号字面一致性**（堵 MP21 型）：期望中的每个关键记号必须与引文**逐字一致**；禁止翻译；确需翻译必须显式声明、标记高风险，并**加测一条「原记号直出」的期望**。
3. **逐字段全量比对**：通过判定 = 输出树全字段 diff 为空；任何字段差异即命中。

## 四、边界声明

v2 修掉这两例后，heldout 家族仍有更深的坑（反直觉边界）。自我出题的自检只能逼近、无法兜底；完全闭合需要**独立验证臂**（另一 LLM 独立出题，与实现臂错开）——协作者方案①的定位。v2 先上（便宜），独立验证作为 heldout 型题目的升级手段。
