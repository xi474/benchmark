# SemanticParallel 严格通过率改进方案

**提交评审 · v1.0 · 2026 年 11 月 23 日**<br>
适用范围为自研 SemanticParallel（SP）、Upstream59 v2.1.0、DeepSeek V4 Pro 普通模式。本文给出拟实施的设计、离线验收和实验登记草案。历史结果与计划试次数分别列示。

## 一、团队要做的决定

**建议把第一项开发投入给独立语义验证。** 对一道题，先让验证者只看公开题面和接口，算出一组有区分力的小输入及其期望答案，封存后再让执行器运行真实候选。若结果不同，根 Agent 拿到能复现的反例，核对题意，在同一工作区修正并复验。业务分支仍按原有策略决定如何拆分。简单题可以用一个手算例子；公开规格不足以确定答案时记录歧义。

**第二项是把反馈提前到首次形成可运行整题时。** 两项分别测试。第一项回答“验证是否找对错误”，第二项回答“找到以后根还有没有时间修好”。新验证者、提前检查和增加并发若一次全部启用，即使得分上升也难以指导后续设计。

首版交付四件东西：可单独开关的独立验证协议、能绑定到最终提交版本的反例与复验记录、包含异常路径的断网验收、同题配对的严格通过率与资源对照。先建议评审和实施离线部分；文中的 24 次、48 次是后续试验设计。

## 二、59 题的失分决定了优先级

| SP 首轮情况 | 题数 | 对方案的含义 |
|---|---:|---|
| 整题严格通过 | 25/59 | 新机制要跟踪“原本通过、改后失败”的题 |
| 未严格通过 | 34/59 | 每题都至少失掉一个核心 API 用例 |
| 公开已过、仍未严格通过 | 25/34 | 8 题仅失 API，17 题同时失 API 与其他登记检查 |
| 公开未通过 | 9/34 | 需要保证业务能执行、合并后能构建、失败能回到根修复 |
| 距严格通过只差一至两项 | 7/34 | 上述 25 题的子集。5 题差一项，2 题差两项，合计缺的 9 项都是核心 API |

这 7 题为 MP19、MP24、MP26、C031、C055、C074、MS02。现有公开失败重放覆盖不到这些题；即使计入重放，它们仍有同样的缺口。若只补齐这 7 题并保住原有成功题，严格通过数会从 25 变为 32；这是算术情景。历史重放实际覆盖 9 题，其中 6 题采用新成绩，全库严格通过从 25 增至 28，须另列。SP 首轮与 DSH 同为 633/803 个核心转换用例通过，DSH 严格通过 36 题。由此将**首轮严格通过率**定为主指标，逐用例准确率作为辅助指标。[逐题原始统计](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/results/upstream59-v21-semserve-vs-six-harnesses-20261123/task-metrics.json) · [计分复核和耗时配对](evidence/sp-tradeoff-evidence.json)

**例子。** MS41 的公开题面要求每轮投票先抽一次环境，全轮共用。SP 在根集成时先平均各环境的单票分布，再计算整轮投票。设两个等概率环境，甲环境每票必投甲、乙环境每票必投乙。两张票在同一轮必定相同；先平均再逐票抽样会算出一半概率不同。SP 的分支和根都做过测试，公开检查通过，正式核心 API 仍为 5/11。DSH 在同题把 500 个随机输入的完整输出逐例与参考程序比较，正式为 11/11，但对照过程中发现的首个错误来自参考程序本身。因此方案既要能发现这类组合错误，也要能保护正确实现免受错误测试的诱导。此处案例供开发者诊断，运行时验证者只收到本次任务的公开材料。[MS41 公开题面](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/tasks/MS41/instruction.md) · [三套 trace 对照与反例](sp-codex-dsh-reward-tradeoffs-20261123.md)

## 三、SP 已有的能力和需要补的部分

- **正式基线。** 在 C/MS 冻结方案中，业务子会话继承模式为 fork，自检为 `serial_p02`，自检预算 300 秒。它已要求按公开要求推导小规模参考解、覆盖边界、真实执行断言、修复确认的候选错误。根合并检查点、公开交付检查、工作区版本校验和最终复验也已存在。已归档首轮 50 题进入自检，自检开始时点占各题执行总时长的中位数为 70.5%，其中 7 题记录自检预算耗尽。其他题族需要逐一核对其实际冻结配置。[冻结方案](https://github.com/xi474/benchmark/blob/39ffdc9f498e9150b30a07401d30276d8d6c25df/semserve/20261121-v21-cms30-v1/experiment_plan.json#L188) · [现有自检指令](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/visible_contract_check_live.py#L249) · [自检审计](evidence/strict-trace-audit.json)
- **可复用原型。** D1 已能提取公开契约与接口签名、复制私有候选并执行检查。D2 已有失败分类、保留反例、同版本重放和无进展抑制。当前 D2 整套路径还包含至少 3 个评审组、至少 30 个用例、可并行 3 个工作者和 600 秒评审时钟。直接切换会同时改变方法与资源。D1 从当前工作区扫描指定文件；要证明验证者在封存前看不到实现，还应从**任务启动时冻结的公开材料白名单**构造输入，并核查它实际收到的上下文。[D1 输入与候选副本](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/visible_contract_check_d1.py#L79) · [D2 预算与数量](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/visible_contract_check_d2.py#L16) · [D2 失败修订规则](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/visible_contract_check_d2.py#L172)

## 四、首版工作流

| 步骤 | 谁负责、能看到什么 | 输出及下一步 |
|---|---|---|
| 1. 挑要验证的规则 | 验证者只读原始公开题面、冻结接口签名、公开输入与有文档的行为。使用独立的初始上下文，检查父历史、自动摘要、工具回执、共享目录均未带入实现 | 选 1–2 条最可能区分两种合理实现的规则，记录公开依据。可选边界、非法输入、状态更新、跨组件约束或不变量 |
| 2. 封存预期 | 验证者在私有目录写最小输入、预期或不变量、推导方法。需生成输入时一起记录算法、种子和数量。确定性问题优先手算或小规模枚举 | 运行时记录原始输入、期望、参考程序及依赖的摘要、时间和版本。参考程序先独立运行；仅保存哈希不足以复验，须同时留存实际材料 |
| 3. 执行候选 | 独立执行器取得只读候选快照，在临时可写副本上通过公开入口调用真实实现。预期计算环境不导入候选；执行器分别接收已封存期望与实际输出 | 每个可执行用例记录输入、期望、实际、退出状态和候选哈希。检查需要比较完整结构还是有限性质，由公开规格决定 |
| 4. 裁决不一致 | 根 Agent 看失败输入、公开条款和最小差异。先复现，再决定修业务、修参考、修输入或保留歧义 | 确认业务错误后由根或原负责分支修改；保留原反例。修参考产生新版本，保留原判定及理由，不能记为业务修复 |
| 5. 同版本复验和交付 | 根在正式提交工作区修复并重建。对修后版本重跑原反例、受影响的组件或接口、公开整题检查和既有最终检查 | 绑定代码、公开入口、依赖与交付产物版本。候选相关内容变化即废止旧回执。正式隐藏评分在 Agent 结束后由原评分器执行 |

两条实践规则很重要。**验证自己的参考算法也计入预算。** 对参考实现先跑一个能手算的锚点，遇到矛盾优先缩小输入。**已有分支写的测试可以保留。** 新评审优先查局部单测难覆盖的跨组件约束。规格只能推出某个不变量时就检验不变量，无法推出唯一顺序或唯一输出时标为歧义。用例多、子 Agent 多或自检全绿均不直接增加正式评分。

### 失败、回退与预算

| 情况 | 处理方式 |
|---|---|
| 已确认候选违反公开规格 | 返回原根并保留反例。相关源码修订后在新副本复验，记录是否真的改变业务行为。相同版本与相同失败不重复消耗修复轮次 |
| 参考程序或生成器自身错误 | 保留失败材料和初始期望，允许一次有公开依据的修订。仍不能裁决时记“未解决”，让根按原完成流程收尾 |
| 规格歧义、评审超时、无可执行期望 | 各自记明原因，附加检查结果保留未知。回到原公开、完整性及最终检查；附加检查的失败不能伪装成通过，公开失败和完整性失败仍沿用原处理 |
| 根工作区在检查期间变化 | 保留原版本记录，废止对当前提交的有效性。用同一封存输入在新版本上复验，避免拿旧版本的绿灯提交新代码 |
| 预算不足或凭证故障 | 保留检查点、已发请求、已结算及未知用量；停止新付费调用。正式试次按原结果计，恢复或补跑另记 attempt |

建议首版每题至多一个额外评审席位、一份小用例集、两轮有相关改动的候选修复；可从至多 8 个确定性对照输入起步，按预检冻结。上限涵盖所有子检查，**不设置最低创建数或最低用例数**。对照两臂按同一每题总时钟、API/成本与 CPU 配额记账。C/MS 原 300 秒自检时钟内建议为同类附加评审最多分配 90 秒，并在运行前实测仍为原收尾留足时间；原试次总时钟优先。其他题族按登记预算取相同比例并设相同上限。90 秒是工程初值，其影响在诊断两组中对齐。

## 五、改哪些代码、分几个版本交付

**版本 1：独立期望与可复现反例。** 在现有自检路由旁增加一个可关闭的评审协议。复用 D1 的输入提取、候选副本和执行器，以及 D2 的失败证据和同版重放。新增最小接口是“提交独立期望”“在指定候选上对照”“向根返回可复验差异”。预算、调用权限、账本、快照均走现有运行时。业务分支继续按原策略运行；验证者的会话需显式验证不会继承业务 fork 历史。关闭该协议时旧自检仍可单独运行。[自检模式选择](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/output_guard_live.py#L16) · [复用候选执行](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/visible_contract_check_d1.py#L98)

**版本 2：前移第一次根反馈。** 根收到已物化分支，或单根题第一次形成完整入口时，按本题冻结的公开入口重建并检查。先核对入口与依赖就绪，再在独立快照开始检查，相同候选去重。早期检查返回结果，不提前调用 `finish_task` 或接管原终止自检；候选继续变化时废止旧结果。确认收益后再考虑让参考准备与实现真实重叠。并行收益以两个时间段的实际重叠和完整 E2E 衡量。[根合并检查点](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/runtime/src/agent_runtime_demo/parallel_runtime_v2.py#L815) · [公开检查及最终复验](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/output_guard_live.py#L34)

**独立可靠性修复。** 第一轮可以并行做离线修复，A/B 任一阶段须两臂采用相同版本。C069 型协议拒绝按“同代、同一字段/约束”计数，首次给可操作反馈，到限恢复根的业务工具并保留已合并状态。局部编辑与写前版本校验先覆盖“根修改分支合并后的已有文件”，防止覆盖过期版本。受管长验证先支持退出码、增量输出、候选版本和截止清理。只有 trace 出现对应的阻塞才启用相应变体；清单、长会话摘要和全面后台化留到后续单独评估。[可靠性设计和 C069 事件链](sp-accuracy-reward-improvement-plan-20261123.md) · [Codex 与 DSH 机制实证](sp-codex-dsh-reward-tradeoffs-20261123.md)

## 六、先断网验收，再决定是否做付费配对

**离线验收**使用人工编写的公开规格小题、已存候选及脚本化模型返回。至少覆盖下列结果：

1. 在父历史、摘要、候选源码和候选输出放入标记，核对验证者封存前的实际请求与可见文件均不含标记。封存前无法调用候选、读取其工作区或通过共享路径拿到结果。
2. 正确候选通过；注入一个已知跨组件语义错误后，有独立生成的最小输入可以区分，根修复后用**原输入、原期望**复验成功。再用另一种符合同一规格的正确实现检查误报。
3. 故意注入参考解错误、生成非法输入、规格歧义，各自正确分类，原业务代码得以保留。覆盖仅打印成功、跳过断言和照抄公开常量的情形，均不能记为独立验证成功。
4. 注入过期产物、候选并发变化、评审超时、余额中断，核对版本失效、进程清理、账本和原完成流程。确认关闭新开关能重现旧回放。正式 verifier、隐藏用例、历史分数绝不进入 Agent 输入。

产物为两臂镜像与挂载哈希、模型和推理配置、实际工具清单、封存材料、逐事件样例与异常回执。通过依据是上述可复验行为。若历史镜像无法原样恢复，采用同一可复现重建镜像新跑对照，并标明与历史版本的差异。

### 两阶段实验登记草案

| 阶段 | 任务与规格 | 实际比较的问题 |
|---|---|---|
| **诊断，24 次** | MP19、C055、MS41、MS11、C069、MS23；6 题 × A/B 两臂 × 2 次。建议先做 MS41、MS23 各一对，共 4 次，计入 24 | A、B 相同的附加评审席位、调用上限、原收尾流程、根检查时点。A 生成期望时可看到候选，B 只见公开输入且必须先封存。两臂用同一对照执行器。估计的是**信息可见性和封存顺序这一协议**的作用 |
| **冻结版本验证，48 次** | 另 12 题 × 原 `serial_p02` 基线 / 冻结交付版 × 2 次。具体题族的原策略随版本核验。源自 4 个家族，清单见下 | 两臂均新跑，使用相同资源总额。回答团队实际切换整套交付版能否提高严格通过率，包括附加评审占用原收尾预算的影响 |
| **可选后续** | 单独评估提前根反馈：固定版本 1 与其他预算，只变时点。若要估计两种改动的交互，保留“均关、仅独立期望、仅前移、两者均开”四组 | 首两阶段共计划 72 次；此项及任何全库复验另行登记和估算 |

诊断题有不同用途。MP19、C055 查看能否发现最后一个语义缺口；MS41 查看组合约束；MS11 查看集成失败；C069 核对“未能进入验证”也进入分母；MS23 专门检查原本正确的结果会不会退化。4 次技术试点的放行依据是隔离、计量、版本与实际执行证据齐全，模型答错仍保留为正式结果。诊断样本的得分不用于估计整库效果。

**12 题冻结候选清单。** MP20、MP21、MP17、MP09、MP18；N11；C066、C062（中等），C011、C067（困难）；MS14、MS30。抽取前剔除本方案诊断及前述报告重点举例的 25 题¹，然后按“家族 × 冻结计分难度”分层，层内按 `SHA256("sp-strict-v1|" + task_id)` 升序取前 5、1、2、2、2 题。这 59 题已有历史分析，所以称“冻结后未用于调参的评估题”。执行验证阶段后再根据这 12 题改代码，就要另找一批题验证。报告列原始逐题和分层结果；需要全库近似值时使用原库权重，并披露开发题排除带来的选择偏差。跨题库推广需另备新题。

## 七、如何判断值得上线

1. **主结果。** 按同题同重复配对，列 B 新增严格通过、B 造成回退、两者皆过、两者皆未过和缺评分。报告净新增数、严格通过率百分点差、题族分层及按任务聚类的区间。每题两次先取均值，统计不把多个 API 用例或同题的两次重复看作独立题。分数缺失保留未知，给出有效配对覆盖、全登记分母及受未知项影响的最好/最坏边界。
2. **评分与业务结果。** 按 `delivery-bonus-50-v1` 逐题调用 [workspace_reward.py](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/scoring/workspace_reward.py)，随数据保留版本、难度权重、完整性、严格通过、登记核心通过数及冻结总数。完整性为真时为权重乘以 `0.5 × K/N + 0.5 × strict`；完整性失败为零，缺整份回执为未知。API acc 单列 A 用例通过数/冻结总数及逐题等权平均；另报 B 接口、D 产物、P 公开检查。从原官方 verifier 取分，自造用例不计入分母。[政策](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/scoring/reward-policy-v1.0.json) · [逐题函数](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/scoring/workspace_reward.py)
3. **机制链。** 以一条反例的稳定 ID 关联公开条款、输入/预期封存时点、首次候选访问、候选哈希、实际结果、裁决类别、代码改动和最终复验；另报验证未触发、不同输入同类失败、参考自身错误、未解决。分别统计有效反例数、促成生产修复数、修后复验数及对应题的正式得分，避免把“多调用工具”误读成有效修复。
4. **时间和费用。** 从统一外层 runner 接收试次到评分及收尾结束记录完整 E2E，单列队列等待、环境准备、业务实现、独立验证、修复、官方评分及阶段重叠。报告中位数、P90、输入/输出与缓存命中 token、CPU、子及辅助模型费用、未知用量。历史 SP 只有执行阶段中位数 247.95 秒，不能据此计算新实验的完整 E2E 改善。报告新增一个严格通过所花的增量成本，净增≤0 时记不适用。
5. **决策。** 离线技术验收通过才进入诊断。诊断阶段至少能展示受控错误的检测与同版本复验；真实题出现可确认反例时审计整条修复链，若只增加测试数量则先查覆盖与误报。验证阶段主看净增及回退任务。可供评审的初始性能目标为配对完整 E2E 中位数和同口径已计量总费用各增长不超过 20%，同时检查 P90 和用量覆盖。20% 是拟议容忍度，须在看验证结果前确定。小样本信号为正、异常有清楚解释时，再考虑扩大配对；效果不稳定、回归集中或用量缺失足以改变决策时，保留旧默认并定向修订。

**建议批准顺序：先做版本 1 与离线验收；再审 24 次诊断；取得证据后冻结交付版并审 48 次验证。** 这样团队能分别回答三个问题：SP 是否更早看清自己的错误、是否真的把错误修到最终提交、每多严格通过一道题要付出多少时间和成本。
