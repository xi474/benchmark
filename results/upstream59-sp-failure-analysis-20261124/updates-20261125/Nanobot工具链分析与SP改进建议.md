**建议先做两项能独立开关的改动。** 第一，让根 Agent 能从最终交付物复现一个具体错误，修后用同一输入重新验证。第二，给已经定位到某个文件、某段旧代码的小修提供简单的精确替换入口，沿用 SP 已有的分支写权限。前者帮助模型看见模块自测漏掉的错误，后者让模型改几行代码时可以省去重写整个文件。能提高多少严格通过率和 reward，仍要在 SP 上配对测量。

## 三、SP 可以怎么改

### 优先级一，让根 Agent 拿到可执行、可复验的失败证据

**可借鉴的能力。** Nanobot 的 `exec` 向模型返回命令输出、stderr 和进程退出码。N22 的发现来自模型读到了内层 Git 错误；仅复制工具返回格式，仍会保留外层退出 0 的问题。历史 SP 首轮 59 题中也筛到 11 题、35 份回显同时出现 Python traceback、输出管道和外层退出 0。这是需要保留内层检查状态的例证，不能据此认定 35 次正式误判。[Nanobot 命令工具实现（安装包定位与指纹）](references/nanobot-source.md#shell) · [历史 SP 筛选方法与逐题记录](evidence/tool-feedback-paths-59.json)

**改在已有的公开检查、根集成和分支交付路径。**

1. 框架直接启动的检查分别保存外层退出码、受控子检查结果、工作目录、输入与预期的引用、候选版本、首条失败断言、完整日志位置。只有可验证的子检查才记通过；任意 shell 拿不到内层状态时记未知。父 Agent 的下一次可行动请求应实际收到摘要和复验入口。
2. 分支交付时分别记录“有哪些文件”和“运行了哪些断言”。根合并后，从新的临时目录用公开约定的方式执行、导入或解包最终产物。验证输入固定，预期取自公开契约、独立计算或外部可见的不变量。避免用生产代码生成预期再和自己比较。
3. 发现错误后，父 Agent 能重跑同一检查。运行时关联修前、修后两份回执及对应候选哈希；提交前核对正式交付物与最后通过复验的产物。任意工作区写入改变了相关输入时，旧回执保留历史标签。复验同一公开检查属于当前试次，不消耗另一次整题重放。

**离线验收。** 构造两个通用夹具：四模块通过但根入口漏产物、打包目录多一层且外层退出 0。两者都必须在根的下一条请求里暴露差异，修后同例通过，最终交付版本匹配。另加一个“摘要长度正确、内容错误”的夹具，验证独立预期确能拒绝错误结果。SP 已有分支交付、根运行时和私有检查入口，可沿用这些组件。[SP 工作区和交付工具](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/runtime/src/agent_runtime_demo/tools/workspace.py) · [分支检查实现](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/runtime/src/agent_runtime_demo/g1_branch_checks.py)

### 优先级二，把已定位的小修做成一个容易选、结果清楚的单文件操作

**可借鉴的能力。** 全 59 题，Nanobot 调用 `edit_file` 125 次、覆盖 26 题；`apply_patch` 4 次、覆盖 3 题。125 次精确编辑都只传了路径、旧片段与新片段。源码还能处理多处命中、候选位置等情况，多处命中告警可能作为普通文本返回，磁盘并未改动。这一点在 SP 适合改成明确的“未写入”状态。[Nanobot 文件工具实现（安装包定位与指纹）](references/nanobot-source.md#filesystem) · [原生调用与返回统计](evidence/nanobot-tool-audit-59.json)

**为什么连自己刚写的文件也值得支持精确编辑？** 按题、Agent、路径和回执顺序复核，125 次编辑中有 123 次此前已由同一 Agent 成功整写过目标文件。其中 112 次（占全部编辑的 89.6%，覆盖 25 题），待替换的旧片段在该 Agent 最近一次整写正文中逐字出现且仅出现一次。这里有 15 次此前没有收到该文件的带行号原生读取回显；其他读取渠道仍可能存在。对于 SP，这支持一个具体取舍：若写入后的内容版本仍一致，Agent 可以直接替换自己刚写过的唯一片段，省去一次为取得编辑资格而重读。另一分支或 shell 已改动文件时，仍需重新校验当前内容。[逐次编辑记录](evidence/nanobot-edit-anchors-59.json) · [离线复算脚本](evidence/nanobot-edit-anchors-audit.py)

**复用 SP 的写权限、补丁后端和审计。**

1. 模型接口首版只需 `edit_file(path, old_text, new_text)`。运行时从同一作用域最近一次成功读或写取得内容版本，在实际写入时再校验。旧片段精确且唯一、版本相同、路径归当前写者时才修改。监控记录修改前后内容哈希。SP 参考源码的 `snapshot_token` 使用时间和大小等元数据；提交前的版本校验应使用实际内容。
2. 返回值区分写入、无变化、零命中、多处命中、版本过期、无权限。零或多处命中返回有限的候选行和上下文，供模型定点读取后重试。预览、失败和无变化不登记为新增可交付文件。实际写入应与分支导出或合并的版本检查协调，防止后到的分支静默覆盖。
3. 用正式启动器、模拟模型做断网验收。对父、可写分支和根修复阶段，分别核对实际发给模型的工具说明、调用路由、权限、文件变化与回执。检查“工具有没有出现在菜单”“有可编辑故障时模型有没有选”“写入是否生效”“原来的反例是否转绿”四个分母，便能定位此前注册了补丁、模型却很少调用的问题。

**离线验收。** 一个单文件三行修正可在一次调用内完成。重复锚点、过期版本、同级分支越权、原文与新文相同，都必须产生确定的状态和正确的磁盘结果。已有多文件补丁继续服务需要跨文件一致修改的场景；第一轮消融只切换单文件入口。[SP 参考源码及版本](https://github.com/xi474/SemanticParallel/tree/109a65444b3d4884fe92ec9e1c543b85df34e95d) · [现有工具注册链核查](https://github.com/xi474/benchmark/blob/fa3a0f9c040edc422b7e92b5e2bf75d16e4a8720/results/upstream59-sp-failure-analysis-20261124/SP%E5%B7%A5%E5%85%B7%E4%B8%8E%E9%AA%8C%E8%AF%81%E6%9C%BA%E5%88%B6%E9%80%82%E9%85%8D%E6%8A%A5%E5%91%8A.md#tool)

### 优先级三，支持从错误位置定向读取，单独衡量它节约了多少

Nanobot 支持按行读文件和在文本搜索中取邻近上下文。轨迹中共有 1,511 次 `read_file` 调用，只有 3 题的 7 次显式指定了行段。17 题观察到工具真正重叠，45 对重叠全部发生在文件查找或列目录之间，59 题均未观测到创建子 Agent。这些数字足以支持实现一个低成本定位接口，也限定了可以对 reward 作出的推断。[实际读取与并行证据](evidence/nanobot-batches-59.json) · [四系统工具与子 Agent 记录](evidence/four-toolchains-59.json)

SP 已有 `read_file` 和 `search_text`。建议先让搜索命中返回路径、行号、少量邻近行和版本，支持按回执中的行号继续读；截短的日志保留尾部错误与完整日志引用。用“从收到失败到首次读中目标代码所需工具轮数”和“输入 tokens”验收。若这两项没有改善，可以单独关闭；不必为本轮目的改委派策略。

## 四、如何验证这些改动提高的是严格通过率

**先离线跑通，再做四臂同题配对。** 以同事这次完整部署为共同基线，先冻结实际 commit、挂载文件摘要、工具菜单、模型模式、预算及重放选择规则。A 维持现状，B 只开启根的失败回执与同例复验，C 只增加单文件精确编辑，D 两项同时开启。四组沿用同样的既有编辑后端。若部署基线已经提供单文件替换，C 和 D 只增加本方案的内容版本保护与可定位回执；拆出改名或增加别名时须另设开关。定向读取另作效率消融。离线夹具可以用上述三题启发设计，正式题面、评分器和隐藏检查始终与解题侧分开。

- **研发验证**先选 MP03、N22 检验整题入口，MP01 检验断言强度；选新 SP 已过而 Nanobot 未过的 C011、MS30、N24 作回归保护。训练式地针对这几题调通后，正式有效性应在未参与调参的题上另报，并保留全部 59 题配对结果。
- **成败指标**逐题报严格通过的新增与回退、核心 K/N、API A 分项和工作区 reward。首轮和按固定规则重放后的选定结果分开。只有首轮正式评分、分轮完整性和采用原因齐全，才能解释重放挽回了多少。
- **机制指标**按机会计数。分别报告出现可复现失败的题数、父请求收到具体证据的题数、实际修改生产文件的题数、原例修前失败修后通过的题数，以及最终交付仍含该修改的题数。没有检查证据时记未知。
- **代价**同时看完整 E2E、模型输入/输出 tokens、含重放的估算成本及额外检查耗时。根复验可能提高完整性，也可能拉长关键路径；精确编辑可能减少重复读写，也可能引入过期拒绝。先看同题收益和代价，再决定是否设为默认。

**第一项可交付成果**是让一个通用夹具在分支检查全过时仍能暴露整题错误，由根在原权限内修正生产文件，用同例验证，并交付验证过的版本。这个演示检验的是一条完整修复路径。对严格通过率和 reward 的提升幅度，留给配对评测回答。
