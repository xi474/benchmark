**现在的实施优先级有三处调整。**

1. **先复盘回退，再扩大门控。** 8 道失去严格通过的题里，7 道最终公开检查通过且未标重放。MP22 从 34/34 降为 19/34，MP03 从 32/32 降为 23/32，是优先排查的两题。逐项对齐首个正式差异、交付版本和父任务实际收到的回执。另一道 C007 从 12/12 降到 0/12，标记重放且最终公开未过，应单独调取两轮的公开检查、产物与终态。这三题有助于区别执行/交付异常与公开检查漏项；当前不能从 K 单独判定原因。
2. **已修好的题保留为回归保护。** C055、MP19、N24 本轮均严格通过；C074 也已翻正。下文 C055 的旧错例仍适合作离线演示，但新增机制想证明自己有增量，应看新基线上尚失分的题，如 MP24（36/37 降到 31/37）或 MP26（仍为 38/39），同时保住已翻正题。
3. **补齐归因材料后再消融。** 取本轮的实际部署清单、逐 attempt 的 score（含完整性及 A/B/D/P）、公开结果和重放选择、父子出站消息与文件摘要、计时阶段和费用明细。先在最新配置上验证“父收到哪种证明”和“根是否复验真实入口”；实施方案中的 B/C/D 开关只计相对于该配置的增量。附件不支持把这次 +2.326139 与早先所说的“+0.4”合并解释。

**第一版要能演示这样一件事：两个分支都通过了自己的测试，根 Agent 却在合并后的真实入口发现了错误。它能定位生产代码、完成局部修正、用同一输入复验，并提交刚刚验证过的文件。** 把这条路径做通，比同时添加更多工具、更多自检提示更容易判断哪项改动有效。

历史 SP 首轮有 55/59 题出现跨分支模型请求重叠，166 份成功文件交付回执只确认了文件完整性。最后一次有限自检通过的 37 题中，19 题正式严格未过。SP 和 DSH 都通过了 633/803 项核心 API 检查，严格通过却分别为 25/59 和 36/59。建议优先改善分支到整题之间的验证。局部编辑也值得做，但要独立计量。[四套 Harness 的完整对照与原生轨迹](四套Harness工具链对照与SP改进方案.md)

## 以 Nanobot 为参照，SP 应该先改哪些工具

将附件中**昨晚新 SP 的 selected** 与已归档的 **Nanobot 0.3.5 正式选定试次**按相同 59 题配对。双方严格通过 19 题，仅 Nanobot 通过 13 题，仅 SP 通过 10 题，双方均未过 17 题。这次对照中的 Nanobot 没有实际创建子 Agent。两边运行和重放条件不同，以下用这些题寻找值得借鉴的动作，单项收益需在 SP 内部测量。[本次 59 题配对及调用数据](evidence/nanobot-vs-sp-retest-20261125.json)

**13 道仅 Nanobot 通过的题，13 道都实际调用了 `exec`，5 道用了 `edit_file`，0 道用了 `apply_patch`。** 这 5 道为 C007、C033、MP03、N17、N22。另 8 道仍可经整文件写入或 shell 改实现，因此这个计数只说明工具选择。全 59 题中 `edit_file` 125 次、覆盖 26 题，`apply_patch` 4 次、覆盖 3 题。建议先优化“检查输出能否驱动下一步修改和复验”，其次降低单文件小修与定点读取的操作成本。[Nanobot 逐题调用与返回](evidence/nanobot-tool-audit-59.json) · [四系统工具清单](evidence/four-toolchains-59.json)

| 优先级 | Nanobot 的证据 | 在 SP 上怎么做 | 验收指标 |
|---|---|---|---|
| 1．执行后能复现具体故障 | `exec` 把 stderr 和退出码送回模型。N22 的外层 Python 退出 0，但模型从内层错误找到产物缺陷；MP03 用同一命令验证缺失报告从失败变为通过 | 扩展已有 shell/检查回执，保存工作目录、验证入口、输入/预期引用、产物摘要和首差；对框架明确启动的必需子命令单收退出状态。根可在干净副本重建后按相同条件复验。普通任意 shell 无内层证据时记未知 | 预置“外层 0、内部调用失败”的公开夹具，确认根下一请求看到首差；修前、修后回执能关联同一检查；最终交付文件能对上复验过的版本 |
| 2．低成本精确修正单个生产文件 | `edit_file` 接受旧片段、新片段；可提示重复匹配的位置和最近窗口。MP03 改 3 行接通整题产物，N22 改归档路径 | 在同事现有单文件替换入口上验证权限，补版本校验和结构化回执，默认唯一精确命中才写。无命中显示候选位置及差异，多处命中先重读；按行提示仍须核对旧文及读时内容哈希。输出 `applied/unchanged/ambiguous/stale`、补丁前后哈希与行数 | 有编辑机会时的选用率、首次正确改动率、原例转绿率、最终交付保留率分别统计。Nanobot 的多匹配告警可以是普通文本，SP 应显式标记“未写入” |
| 3．沿命中行拿到上下文 | `grep` 可带上下文、`read_file` 能按行段读取。MP16 有“读取两个相邻行段 → 修改同一实现”的实证。1,511 次原生读文件中 7 次显式指定行段 | 扩展现有 `search_text/read_file`：命中行、有限邻域、文件版本、下一行。长命令错误回显同时保留头部、尾部和原始日志引用。内容已变或上次正文已从模型上下文移出时允许重读 | 衡量从错误回执到首次读中目标代码的轮数、读取 tokens、过期编辑拒绝率；分页和读去重单独观察成本 |

**MP03 是首个落地夹具。** 原生轨迹 242–243 的模块检查打印了四个 `MODULE_OK`，整题随即因缺少 `outputs/final_report.json` 失败，退出 1。246–247 用 `edit_file` 在生产文件 `run_all.py` 中接上 `final_report.py`；250–251 重跑相同的 `python3 _run_check.py`，得到公开检查通过、退出 0。独立评分 Nanobot 为 K 32/32、API 21/21；新 SP 为 K 23/32。SP 可用通用测试复现“各模块都成功，但根入口漏产物”，作为改进验收。新 SP 的具体 9 项失分原因仍需它的原始评分和 trace。[MP03 原生轨迹](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/results/upstream59-v21-native-traces-dsh-codex-nanobot-20261123/nanobot/MP03.zip)

**N22 验证最终使用者拿到的东西。** 原生轨迹 234–239 在临时目录解包最终 bundle，发现仓库多包了一层目录，根目录执行 Git 报错；进入唯一子目录，才找到可用的仓库。242–243 在 `products/gitutil.py` 改为按子项打包，250–259 重建新 bundle，换临时目录再次按相同方式解包，根层可直接看到 `.git` 和业务文件。Nanobot 正式 K 19/19、API 9/9，新 SP K 15/19。Nanobot 在这题选择“从消费端打开刚交付的文件”是模型实际采取的动作。为 SP 提出的新增功能，是让根运行时保留该消费入口和产物版本，修正后可再次执行；附件尚不足以判定新 SP 遇到同一个目录问题。[N22 原生轨迹](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/results/upstream59-v21-native-traces-dsh-codex-nanobot-20261123/nanobot/N22.zip)

**哪些做法移植时需要改。** MP01 中 Nanobot 真修了路径并复验成功，与新 SP 同为 K 27/28。Nanobot 的 API 已过 17/17，公开检查也过，但正式最终报告产物项未过。轨迹 268–269 的自测检查了摘要字符串的长度；长度正确仍可能是错误内容的摘要。在 SP 做产物验证，建议从公开条款推导独立预期，或者从实际消费入口读取交付物并检查外部可见行为，另记“原例已修”和“整题严格通过”。本次附件没有给出 SP 在 MP01 的具体失败项。[MP01 原生轨迹](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/results/upstream59-v21-native-traces-dsh-codex-nanobot-20261123/nanobot/MP01.zip)

Nanobot 的文件查找并行确实在 17 题发生，子 Agent 创建为 0；已有数据也不足以给它的读缓存或多文件预览排出 reward 优先级。SP 保留已有语义并行、所有权和重放机制。在专门测 Nanobot 工具的消融中，第一步只开可复验的执行回执，第二步在相同配置上再开精确编辑，最后独立评估定向读取。C011、MS30、N24 等新 SP 已过而 Nanobot 未过的题作为回归保护。[Nanobot 文件编辑实现（安装包定位与指纹）](references/nanobot-source.md#filesystem) · [实际并行及分页读数据](evidence/nanobot-batches-59.json)

## 团队按什么顺序做

| 合并单元 | 负责模块 | 可独立验收的交付物 |
|---|---|---|
| 0．确认共同基线 | 启动器、评测 | 实际加载的代码和配置，以及父、子、根自检各一次模拟请求与工具执行记录 |
| 1．分支私有测试和父回执 | 分支执行器、消息构造 | 一次调用执行私测；父 Agent 下一次可行动的请求里有候选版本、局部测试结果、尚缺的验证 |
| 2．根集成与同例复验 | 根运行时、公开检查 | 封存输入和预期、修前修后的实际结果、干净重建后的交付清单；串行和有分支任务均能走通 |
| 3．精确编辑和就近读取 | 工作区工具 | 单文件小修复用已有补丁后端；从错误行继续读；拒绝歧义或过期修改并给出可执行的下一步 |
| 4．独立消融 | 评测 | 按题配对报告严格通过、API、reward、完整 E2E、tokens 和成本，保留首轮、重放和异常 |

先合入 0 和 1，完成断网验收，再接 2。3 可并行开发，单独开关。以下新增的工具名和字段是设计草案。源码位置以已核验发布提交 `109a6544` 为锚点；同事补丁版及历史容器挂载需按实际版本对照。

## 1．分支测试一次，交付时让父任务看见它证明了什么

## 4．交给开发者的断网验收单

使用与部署具有相同隔离能力的 Linux 容器、临时任务模板及模拟 provider，走正式启动器、工具执行和最终请求适配层。下面是拟议新版要通过的验收。

| 场景 | 能判定通过的证据 |
|---|---|
| 两个并发文件分支在同名私有路径写测试 | 各自收到自己的回执；根与同级业务文件未被测试污染；取消后无遗留进程 |
| 导入失败、零发现、全跳过、断言失败、正常通过 | 前三者无业务通过证明；断言失败能关联首差和真实候选调用；正确实现得到绑定当前版本的绿色回执 |
| 不可信或过期的成功说明 | 子总结声称通过、单独打印成功字样、另一 attempt 的回执、旧文件版本都不能改变验证状态 |
| 更换测试或依赖、上游到齐、并发改文件 | 改动相关文件后旧证明失效；无关分支的有效证明保留；真实上游到齐后可将待办升级为实际入口已验 |
| 父请求投影、压缩、恢复 | 截获模拟传输的请求体，核对第一条可行动的父请求仍含正确回执 ID、版本和待办；分别测正常上下文、强制压缩、恢复，以及步数耗尽后的自动交付路径 |
| 正确实现、等价改写、单缺陷候选 | 在相同输入和预先封存的独立预期下，两份正确实现绿，缺陷候选红；公开允许的无序输出按相应比较规则处理 |
| 内层失败、旧产物、源文件中途变化 | 外层正常退出不能遮住必需子进程失败；预放正确旧文件不能让坏实现通过；换版后重新核对再交付 |
| 修前修后归因与纯串行任务 | 归档能对齐同一输入、预期、入口的两次结果及生产文件 diff；仅改断言记作参考修订；无分支时根也能封存 |
| 局部编辑与定向读取 | 唯一匹配成功，歧义/过期/越权保留原字节；失败可定位；旧正文退出模型上下文后能重新读取 |
| 预算和旧结果 | 超时保留已执行数、失败阶段与未知项；各开关关闭时保留旧协议及旧 attempt 的读取语义，历史成绩可独立复核 |

可直接扩展现有 [分支交付测试](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/tests/test_branch_test_delivery.py)、[G1 隔离测试](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/tests/test_g1_branch_checks.py)、[根检查测试](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/tests/test_g1_root_checks.py)、[反馈投影测试](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/tests/test_selfcheck_feedback_projection.py)及[断网回归入口](https://github.com/xi474/SemanticParallel/blob/109a65444b3d4884fe92ec9e1c543b85df34e95d/experiments/handshake_speculation_v1_report_gate_v1/run_tests.py)。在新版本中保存测试及模拟出站摘要；不覆盖旧实验材料。

**第一位开发者的代码阅读顺序。** 在实际加载的版本中依次找这四条链，按方法名定位，避免在未挂载的运行时副本里改对了代码。

1. 分支执行：`g1_branch_checks.maybe_execute_branch_shell → BranchMirror.run → _unit_check`。提取共用的私测执行逻辑，保留现有隔离与调用上下文。
2. 交付签收：`FileBranchChecks.complete → complete_g1 → artifact_fields → _artifact_satisfies_branch_completion`。在此绑定分支、版本和证明，复用现有签收与过期校验。
3. 父任务可见：`_model_facing_tool_result → 根消息状态 → 上下文压缩 → provider 最终序列化的请求`。在模拟传输端检验短回执，不以压缩前的 trace 为最终凭证。
4. 根验证：`_v2_activate_root_integration_checkpoint` 提前挂上待办；`make_public_checker.check` 覆盖最终公开复验与封存。在两者间复用同一份按候选版本索引的记录，纯串行和恢复后的请求均可查回。

## 5．怎么判定对 reward 有效

**分别做可解释的配对。** A 为已复现的本轮完整配置。B = A + 分支私测和父回执；C = B + 根真实入口同例验证；各项只补 A 尚未实现的部分。同题同重复比较 B 对 A、C 对 B。D 为单文件精确替换；若 A 已有兼容后端，直接比较 A+D 与 A，否则两臂均在 A 上安装同一后端，仅切换 D。若想回答“只改根验证是否就够”，另测 A + 仅根验证，才能拆出分支回执与根验证的交互。读文件分页和输入副作用观测各自开关。各组记录实际启用状态，按分配的全部任务计入主比较。

**建议的首个试点。** 已知 C055、N24、MP19、MP24 用于离线开发，并挑选原严格通过的题做回归保护。随后可在 8 道预先冻结的题上只比 A 与 B，每题每组两次，共 32 次。先看父回执是否送达、是否出现误报及开销，再决定是否扩大到 59 题和 C、D。8 题是工程试点建议；已分析过的 59 题属于已知题库回归，泛化收益用另行预先封存、未据以设计改动的题或公开变体验证。

| 读数 | 分母与口径 |
|---|---|
| 质量 | 全部配对题登记新增严格通过、由过转败、无变化及缺评分。完整配对给出净增及逐题清单，单侧缺失给出覆盖和可能范围。API 只列 A 通过数/冻结总数。正式 reward 逐题用 `workspace_reward.task_reward`，登记冻结难度、完整性、严格标志及 A/B/D/P 核心检查通过数与固定总数；整份评分缺失留未知 |
| 机制 | 按需要证明的文件分支统计实际执行率；按有接收机会的父决策统计正确版本回执送达率；按有可复现生产错误的机会统计同例改后转绿率、修复进入最终包的比例。分别记误判、仅改测试、未触发和缺日志；分母为零记不适用 |
| 时间、tokens、钱 | 新批完整 E2E 从 trial 启动到独立评分结束，分列排队、执行、分支测试、根重建和评分。跨分支重叠看时间区间并集。计父、子和辅助模型的输入/输出、缓存、费率与是否有已结算量。历史 SP 仅有执行阶段时间，辅助模型费用不全 |
| 试次与重放 | 固定题包、模型与辅助模型、权限、父子共享预算、并发资源和评分器，配对顺序随机交错。首轮与按相同登记规则采用重放后分别出表，所有 attempt 的资源开销进入相应策略总账。同一 attempt 修后复验与另起 attempt 重放分别计数 |

**发布决策。** B 若只提高送达率，下一步检查父是否用了正确版本、是否选了能区分实现的真实入口。D 若只减少编辑 tokens，归为效率改进。要将“提升严格通过率”写成实验结论，需要展示配对的严格通过变化、reward、缺失与不确定性；要决定是否作为默认配置，还要审查完整性回退、原通过题退步以及预先约定的成本与 E2E 容忍范围。出现回归时可只关闭对应开关并按原登记保留异常。本手册给出实现与判据，新版本的增分幅度仍待实测。[工作区评分实现](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/scoring/workspace_reward.py) · [既有总账、重放及计时边界](https://github.com/xi474/benchmark/blob/00d32858637689c0668c71303d4d5b79d00b1093/results/upstream59-v21-semserve-vs-six-harnesses-20261123/README.md)
