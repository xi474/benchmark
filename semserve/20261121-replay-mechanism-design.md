# 公开失败重放机制设计 + 实证增益分析（2026-11-21 18:10 修订：上限 1 次重放）

## 一、机制设计（Retry-on-Public-Fail，上限 1 次重放）

### 1.1 触发判定：干净副本重算公开检查（clean-P）

**判定口径必须升级**——当前 output_guard 的公开检查在**原工作区**跑 `check.py`（经 shim 委托 public_check.py），会被"产物短路"骗过（C069 全量轮实证：运行时检查通过、官方 P 失败、work.py 实为 NotImplementedError）。重放机制的触发判定采用与官方评分器同语义的检查：

```
clean_public_check(case):
    work = copy(case.workspace)                     # 剥离生成产物
    work.strip(['outputs/', '__pycache__/', '*.pyc'])
    rc = docker(run, --network none, -v work:/app, -w /app,
                image=task_tests_image, python3 public_check.py)   # C/MS
           or python3 check.py                                      # MP
    return rc == 0
```

- 成本：每次判定一个一次性容器（~2–10s），零模型调用。
- 与官方 P 的差异仅剩 demote(uid)（非 root 运行），判定结果与官方 P 一致（本轮取证已按该口径复现官方判负）。

### 1.2 重放控制器（编排层实现，冻结 runtime 零改动）

放在实验编排层（host 侧 runner），**不触碰冻结的 runtime/提示词/镜像**——重放=完整重新执行一次任务，本来就是编排层动作：

```
receipt = run_actor(task)                  # 首次执行（新容器、全新 agent）
if not clean_public_check(receipt.case):   # 触发判定
    receipt2 = run_actor(task)             # 最多 1 次重放（新容器、全新 agent）
    if clean_public_check(receipt2.case):
        keep(receipt2)                     # 重放通过则采用重放轮
    else:
        keep(receipt)                      # 双失败保留首轮（保守规则）
```

- **选择规则（保守）**：重放轮通过 clean-P 则采用重放轮；双失败保留首轮。不依赖任何隐藏信息。
- **可选增强（oracle-best）**：双失败时用本地代理分（clean-P、B/D 公开输入构建项）择优——只能区分失败轮相对质量，不引入隐藏用例信息。
- **预算护栏**：每题重放上限 1；全局重放执行数上限（如 12）。
- **回执**：每轮 attempt 记 host_receipt + clean-P 判定 + 重放计数（`replay_receipts/<tid>/`）。

### 1.3 容器是否需要重新拉起（2026-11-21 18:10 用户提问的结论）

**重放需要重新拉起容器，且"不拉起"省不了什么**：

1. 成本大头是模型调用：容器启动 ≈2–5s，任务执行 100–600s（DeepSeek 调用主导）。复用容器只省启动秒数，重放的 token 成本不变。
2. 同容器重放需要"重入"支持：冻结入口是一次性流程（模板→/workspace 拷贝、结果目录存在即 `RuntimeError("result exists")`）。同容器重放必须重置工作区+结果目录+重开 agent 循环——改动冻结入口或加 wrapper，改动量大于收益。
3. 前缀缓存收益 <1%：重放对话与首轮仅在 system prompt+任务文本（~15–25k token）上相同，工具观察立即分叉，相对每题 1–3M 输入 token 可忽略。
4. 相邻方案（记录备选）：复用**会话**而非容器——clean-P 失败喂回同一 agent 会话做增量修复（热上下文，runtime 有 selfcheck-repair 先例）。风险：C069 型产物短路正是该会话自选路线，原地修复大概率继续短路；全新重放才摆脱路径依赖。故本设计采用新容器重放。

## 二、实证增益估计（上限 1 次重放，基于 9 题重跑的真实观察）

**触发率**：统一账 59 题中公开未过 9 题（15.3%）——每轮约 15% 任务触发重放。

**重放结果**（9 题实测）：6/9 通过 clean-P（C033、C069、MP01、MP14、MP20、MP25），3/9 仍失败（C011、C039、MS11——两轮观察的稳定硬失败）。

**整体账面变化（保守规则：重放通过则取重放轮完整分数）**：

| 指标 | 基线（统一账） | 重放后（估计） | 变化 |
|---|---|---|---|
| 公开通过 | 50/59（84.7%） | **56/59（94.9%）** | +6 题 |
| 严格通过 | 25/59（42.4%） | **28/59（47.5%）** | +3（C069 3.0、MP14 2.0、MP25 2.0） |
| 总 reward | 78.469/138（56.9%） | **85.362/138（61.9%）** | +6.89（3.0+1.5+1.44+0.17+0.29+0.50） |
| E2E 合计 | 18,480s | ~21,210s | +15%（9 次重放 ≈ +2730s） |
| 总成本 | $18.80 | ~$22.1 | +18%（9 次重放执行 ≈ +$3.3） |
| reward/$ | 4.17 | ~3.86 | 微降 |
| 每严格通过成本 | $0.752 | ~$0.79 | 微升 |

**上界（oracle-best 选择，含 C011 重放分 0.75 替换 0.214）**：reward +7.43 → 85.9/138（62.2%），strict 同 28。

**结构性结论**：

1. **重放对"执行偶发型失败"高效**：MP 家族 4 题的组件崩溃（渲染/级联）重跑全消失；C069 的产物短路路线重跑改走真实现——这类失败占公开失败的 ~2/3，一次重放即可挽回。
2. **对"稳定硬失败"无效且无需第二次重放**：C039/MS11/C011 两轮稳定失败，第二次重放边际收益≈0——**上限 1 次重放是数据支持的正确预算**。
3. **对"公开通过但隐藏崩坏"无效**：C049/C058（公开 ✓ 但 A≈11%）不触发重放——这类缺陷只有隐藏用例能探测，需要"每组件多样例/属性自测"（与 acc 差距分析结论互补）。
4. **单位经济性**：+12% strict、+8.8% reward 的代价是 +18% 成本；reward/$ 与每 strict 单价均微降——重放买的是"下限保障"（消灭执行偶发失败），不是效率。

## 三、实现落点与验证路径

- 实现：`run.py` 增加 `replay` 阶段（run_actor 外层 + clean_public_check 函数），作为独立实验 arm（retry-v1），冻结面零改动；
- 验证：9 个触发题的第一次重放数据已天然存在（rerun9 实验）；保守规则下的账面变化可直接计算，无需再跑；
- 风险：单轮方差意味着"重放后账"本身也有方差（C069 0↔3.0）；论文口径建议报告"重放策略期望值"（用多轮通过率）而非单次实现的账面；
- 相邻备选（未采纳）：会话内修复（热上下文增量修复）——对产物短路型失败有路径依赖风险，见 1.3 节第 4 条。
