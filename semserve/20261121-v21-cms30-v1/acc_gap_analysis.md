# C/MS API acc 显著低于 MP/N 的原因分析（2026-11-21 17:45）

**差距**：C 60.2%、MS 67.3% vs MP 87.3%、N 89.7%（A 类核心转换微平均，统一 59 题）。

## 一、差距的主成分：双峰分布——灾难题拖垮均值

A<30% 的"灾难题"分布：C 6 个、MS 1 个、MP 1 个、N 0 个。

| 家族 | 全量 A | 剔除灾难题后 A | 灾难题 |
|---|---|---|---|
| C | 60.2% | **87.6%（106/121）** | C033/C039/C069（0%）、C011/C058/C049（10–12%） |
| MS | 67.3% | **73.6%** | MS11（10%） |
| MP | 87.3% | **91.3%** | MP20（0%） |
| N | 89.7% | 89.7% | 无 |

剔除灾难题后 C≈87.6% 与 MP 91.3%、N 89.7% 同级——**家族差距的大头不是"MP/N 的实现更好"，而是 C/MS 存在一个"实现系统性崩坏"的亚群**。

## 二、灾难题的错误类型学（对 6 个 C 灾难题的 61 个隐藏用例逐个重放分类）

| 题 | 隐藏用例错误模式 | 语义缺陷 |
|---|---|---|
| C033（MIPS 解释器） | registers[2] 0 vs 4001 ×11、exit_code 0 vs 7、文件写 4142 vs 41424344 | **单一指令语义实现错**——模拟器类任务一处错=全错 |
| C039（贝叶斯网络拟合） | intervened_edges 数量 1 vs 2/3 ×10 | **多边干预规则理解错误**（只干预了一条边） |
| C069 | NotImplementedError ×9 | 组件实现缺失（产物短路，前已证） |
| C011（跨租户 ERP） | orders[*].end off-by-one（6vs5、5vs4）×7、line L2 vs L1 ×2 | **区间端点 off-by-one + 行归属排序错**；公开样例恰好不覆盖该分支（core-10 PASS） |
| C058（分批调度） | batches 数量/内容全错 ×8 | **分批规则理解错** |
| C049（微批训练） | events[1].microbatch 缺失 ×5、梯度数值偏差 ×2 | **microbatch 事件未记录 + 数值精度语义错** |

共性：**单点语义缺陷 + 隐藏用例集中探测该规则 → 近零 A**；公开样例恰好落在没踩雷的分支上，agent 的"公开检查通过"造成了实现正确的假象（C011 core-10 PASS 与隐藏全错并存是最直接的证据）。

## 三、被排除的假设

- **规范长度/密度**：C 中位 2512 字符 < MP 4417 字符；规范字符/A 用例三家族相当（234–406）；C 家族内 Spearman(A率, 规范长度)=-0.37（弱负）——"规范太长"不是解释。
- **用例粒度**：A 用例/题中位 C 9、MS 10、MP 21、N 9——无家族级显著差异。
- **数值容差**：C/MS 契约 tolerance=0 与 MP 一致，无系统性差异。

## 四、剩下的真实差异（为什么 C/MS 更容易踩雷而 MP/N 不容易）

1. **规则代数密度**：C 的灾难题是区间代数（C011）、编码器（C069 token）、CPU 语义（C033）、微批数值（C049）——**一个边界分支错了 A 就崩**；MP/N 的组件是数据投影/聚合类规则，边界分支少且平铺。
2. **验证反馈的可迭代性**：MP 每组件自带 check_module（agent 执行期可逐组件迭代）；C/MS v2.1 虽加了组件 check，但公开样例只有 1 个/组件，**规则分支的覆盖靠公开样例撞运气**——踩不到的分支在交付前不可见。
3. **公开样例过拟合面**：C/MS 的 transform 是单入口整题函数，隐藏用例与公开样例输入分布差异大（边界分支）；agent 对着公开样例实现时，未覆盖分支的错误交付前不可见。

## 五、结论

C/MS 与 MP/N 的 A 差距 ≈ "灾难题亚群（占 C 家族 30%）拖累 + 剩余 14 点的规则代数密度差"。**改进方向指向执行期验证覆盖而非提示词**：让 agent 在交付前对每个已实现组件做隐藏分支式自测（属性检查/变异样例），或任务打包侧在每个组件附多条样例（提高分支覆盖可见性）——这与 J2-a 的"每单元独立验证器"同源，但要把"每单元多样例"加进去。
